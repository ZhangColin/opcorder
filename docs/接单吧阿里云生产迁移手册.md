# 接单吧：从 Replit 迁移到阿里云操作手册

**目标：把现在正常运行的生产系统搬到国内，功能、账号、订单、合同、附件和用户访问效果保持一致，不借迁移做系统升级。**

**迁移后的长期工作方式：本地编辑源码 → 本地Docker开发/测试 → 版本提交及打包 → 国内ECS发布 → RDS按原机制更新。Replit只在本次迁移中提供源码和历史数据，此后不再承担开发、构建、发布、运行、文件访问或备份任务。** 源码及版本历史保存在本地和公司代码仓库；不能把Replit工作区继续作为唯一代码备份。

现有资源：阿里云 ECS、RDS PostgreSQL。存储可选阿里云 OSS、腾讯云 COS 或 MinIO；本文以**阿里云 OSS**写完整主流程，另外两种只替换存储适配与文件导入部分。短信、支付、电子签章继续使用现有国内服务。

本文按实际操作顺序分为三个独立阶段：

1. **本地开发环境**：下载源码，用Docker创建依赖环境，完成必要适配，在本地初始化、启动、修改和测试。可选用已有`prod.dump`恢复到新的本地隔离库；此阶段不部署ECS、不连接在线生产数据库。
2. **生产服务器部署**：将本地验证过的版本部署到ECS，配置RDS、存储、邮件、HTTPS和进程管理；先用独立空测试库/桶验证部署。
3. **历史数据与对象迁移**：再备份、恢复原生产数据库和全部附件，核对路径及数据，最后切换正式访问。

日常版本更新单列为附录。只部署全新系统的，完成前两个阶段即可；迁移现有生产的，必须再完成第三阶段。第二阶段的测试数据不能混入第三阶段的正式恢复库。

这是操作文档，不表示迁移已执行。文中的新变量、新导入脚本和代码片段需要开发人员落实；现有可用命令会明确标注。不要把本地测试库当生产库备份，不要向源生产库恢复数据。

## 怎么照着执行

**第一次从源码搭建：**按下面“本地启动执行单”操作，正文中的完整配置块是唯一主模板；折叠的排错参考仅在出错时查看，不是必做步骤。

**已经跑起来、现在有`prod.dump`：**不要重装环境，直接看[4.8：恢复prod.dump到本地](#local-prod-dump)。每次固定恢复到`jiedanba_local`，先备份再覆盖本地数据，无需每次改数据库名。

按正文的**步骤01～35**依次操作；每一步先看“在哪里执行”，不要将本地命令复制到Replit或ECS。`__...__`和`ECS_HOST`都是待替换占位符。代码块中的命令不能跨机器整段连跑。

- **已有命令**：仓库已有，可以在所需配置准备好后执行。
- **配置模板**：按指定路径创建文件、填写本机/目标环境参数后使用。
- **需要开发**：当前代码还没有实现，先完成对应改动并通过本地测试，不能靠运行配置命令跳过。

**`local-dev`是什么？** 它只是本机存放Docker配置的文件夹，名字可以换，不是另一套项目，也不会复制业务源码。本文固定这个名字，是为了让所有命令路径一致。Docker从这里读取配置，把上一级的原源码目录挂到容器的`/workspace`；你仍在原来的`artifacts/`、`lib/`、`scripts/`中开发。数据库和附件分别存在Docker命名卷，**不是存在`local-dev`里**。

```text
源码根目录/
  package.json、pnpm-lock.yaml
  artifacts/、lib/、scripts/      ← 原业务源码，在这里修改
  local-dev/                     ← 本文让你新建，仅供本机运行
    .env                         ← Docker依赖参数
    api.env                      ← 本地API参数
    Dockerfile                   ← 本地Node/Chromium开发镜像
    compose.yaml                 ← 启动数据库、存储、邮件、开发容器
    nginx.conf                   ← 后续本地构建测试时再创建
```

此目录不上传生产；Docker命名卷不会跟随源码压缩包迁移。以后停容器用`down`，不要加会删除卷的`-v`。本地目录、容器与源码的关系不需要额外搭一套平台。

|---|---|---|---|

| 4 | Replit → 阿里云 | 导出一份生产库和附件，在新环境恢复 | 带真实历史数据的试迁环境 |

| 6 | Replit → 阿里云 | 安排维护窗口，停止旧生产写入，最后备份与同步 | 最终生产数据 |

## 原方案还需补上的项目

“改国内服务→部署→搬库→搬文件→修路径”的方向正确。下面是源码核对后需要补的遗漏，都是为了保持原系统可用，不是增加原生产没有的能力。

| 遗漏点 | 不处理会发生什么 | 本次迁移怎么解决 |
|---|---|---|
| 生产版本和生产配置独立于源码ZIP | 搬了未发布代码或开发配置；登录、付款、签章失败 | 第1节保存源码版本，第5.1节单独整理生产配置，不灌入本地环境 |
| Node/依赖/中文PDF资源 | API启动报模块缺失，或手册/合同相关功能失败 | 第5～6节固定兼容运行时，完整安装依赖，带上字体、手册、worker及SDK文件 |
| 前端不是API自动托管 | 后端健康但首页404，刷新子页面404，AI流式响应积到最后才显示 | 第6节Nginx同时托管SPA、保留/api路径并关闭响应缓冲 |
| 发布包含数据库更新步骤 | 只复制产物会漏掉结构同步；未经验证的同步/seed也可能影响旧数据 | 第4节复用原流程并试迁，第12节按原机制发布和检查 |
| RDS角色/扩展/序列 | 能恢复部分数据但缺表权限，创建新订单时ID冲突 | 第8节核对版本扩展、对象权限、全表计数、关键内容和序列 |
| 不只一个上传入口 | 通用上传好了，头像、后台上传、合同模板仍失败 | 第2节搜索全部直连存储和上传路由调用；每个原入口测试，不只测试一个按钮 |
| 文件metadata和全部公共根 | 文件存在却不能预览、类型不对，或部分课程/图片丢失 | 第9节按manifest完整搬Content-Type、metadata、所有public组及校验和 |
| 数据库里的动态URL和第三方文件 | 用户看到记录但旧文件/外部资源点不开 | 第10节扫描富文本/JSON/模板/模型与工具配置；供应商托管合同继续按原接口访问 |
| 在线备份之后的新写入 | 最后几笔订单、退款或新文件不在目标 | 第11节最终停写备份，同时处理对象覆盖、删除及尚未完成上传 |
| 支付/退款/签章回调和自动任务 | 钱付了订单不更新；两端任务重复处理或计费 | 第11节确认维护期间重试/查单，旧任务停后新任务才开，保留计费水位 |
| 域名、HTTPS、回调、IP白名单 | 网站能用IP访问但客户/供应商不能正常访问 | 保留原域名与证书，完成国内接入；测试ECS出口白名单和回调公网可达 |
| 登录与内存短期状态 | 全员掉登录，或维护中的验证码/上传失效 | 保留域名、JWT密钥、密码哈希和刷新令牌；验证码与未完上传告知重试 |

另外核对了后端本地文件读写：当前发现的本地生成文件是操作手册PDF，可由源码手册和字体重新生成；模板上传使用内存，业务附件走对象存储。**暂未在这些代码路径中发现另一个需要单独搬迁的本地业务文件库**，但仍需运维确认生产是否有源码之外的手工文件/额外挂载目录。若有，列入备份；不能因源码没找到就假定没有。

未确认的是实际生产规模、备份恢复耗时、供应商回调重试期限及生产是否有额外配置。这些在试迁中测量或现场确认，不需要先升级系统，但不能在没验证前承诺不会丢数据。

## 1. 下载源码、配置Docker并启动本地依赖

### 1.1 步骤01：从Replit下载当前生产版本源码

**在哪里：Replit网页 → 本地文件管理器。操作类型：界面操作。**

在 Replit 打开接单吧项目：

1. 确认工作区代码与当前已发布生产版本一致。如果工作区还有未发布的功能，不要顺带迁移，以当前生产版本为基准。
2. 在文件树菜单选择 **Download as zip**，下载并解压。
3. 保留根目录的 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`lib/`、`scripts/`、`OPC操作手册.md` 和两个正式应用：
   - `artifacts/jiedanba/`：前端。
   - `artifacts/api-server/`：后端。
4. 不部署 `mockup-sandbox` 和独立领导力幻灯片。暂时保留完整源码目录有利于依赖安装，不需要为了迁移重整仓库。
5. ZIP **不等于数据备份**：生产数据库、对象存储、生产 Secrets 需分别迁移。不要把 Replit 的 `node_modules` 当作 ECS 可用依赖，必须在兼容 Linux 环境重新安装。

**完成后应得到：** 本地一份源码目录，根目录能看到`package.json`、`pnpm-lock.yaml`、`artifacts/`、`lib/`。如果ZIP外面多套一层目录，进入包含这些文件的那一层，不在ZIP文件所在目录执行后续命令。

### 1.2 步骤02：打开源码目录，创建本地配置文件夹

将ZIP解压为独立工作目录，用编辑器打开仓库根目录。保留锁文件；删除下载包携带的`node_modules`后在Docker内重新安装，不使用宿主机的Node依赖。尚无Git记录时，在本机执行`git init`建立修改记录。源码、修改记录与本地测试数据分别保管，不将凭据加入Git。

电脑只需准备Git、编辑器、Docker Engine/Desktop和Compose v2；Windows在WSL2目录内放源码并执行命令。Node、pnpm、PostgreSQL、MinIO、邮件测试服务、Nginx、Chromium和中文字体全部放Docker里，不必逐个安装到电脑。

**在哪里：本地源码根目录的Bash终端。** 先启动Docker Desktop或Docker服务，再执行：

**这一步只做检查和创建空目录，不安装依赖、不生成配置、不启动任何容器。** `test`是Bash的条件检查命令，`-f`检查文件，`-d`检查目录。下面增加了结果提示；外面的括号让失败只结束本段检查，不关闭你的终端。

```bash
(
set -e
trap 'echo "检查未完成：请处理上方错误，再继续。"' ERR
echo '[1/4] 检查当前源码目录'
pwd
if test -f package.json && test -f pnpm-lock.yaml && test -d artifacts/api-server; then
  echo '通过：找到了项目文件'
else
  echo '失败：请进入包含package.json和artifacts的源码根目录'
  exit 1
fi
echo '[2/4] 检查Git和Docker（这里不安装软件）'
git --version
docker version
docker compose version
echo '[3/4] 准备Git记录和本地配置目录'
# ZIP没有Git记录时，建立本地修改记录；已有仓库不重新初始化
if ! git rev-parse --git-dir >/dev/null 2>&1; then git init; fi
mkdir -p local-dev
EXCLUDE_FILE="$(git rev-parse --git-path info/exclude)"
mkdir -p "$(dirname "$EXCLUDE_FILE")"
grep -qxF '/local-dev/' "$EXCLUDE_FILE" 2>/dev/null \
  || printf '\n/local-dev/\n' >> "$EXCLUDE_FILE"
echo '[4/4] 确认本地配置不会提交到Git'
git check-ignore local-dev/.env
echo '步骤02完成：只是准备好了目录，数据库和应用还没有启动。'
echo '下一步：继续步骤03～06，创建.env、api.env、Dockerfile、compose.yaml。'
)
```

**预期：** Docker客户端和服务端都能连接，Compose显示v2，最后显示`local-dev/.env`被忽略。任一检查失败先处理，不继续创建容器。Windows须在WSL2的Linux文件目录中执行，不能把下面Bash当PowerShell运行。

**已经执行过旧命令且没有报错的，不用重做目录。** 接下来仍留在源码根目录，依次执行步骤03～06的四段`cat > local-dev/...`命令，填写参数，再进入步骤07。每段`cat`才会真正创建对应文件。`.env`文件在部分文件管理器里默认隐藏，可用`ls -la local-dev`查看；不要把含密钥的文件内容贴到聊天里。

| 执行到哪里 | 实际得到什么 | 此时能否打开系统 |
|---|---|---|
| 步骤02 | 空`local-dev`目录和隐藏的Git忽略规则 | 不能 |
| 步骤03～06 | 四个本地配置文件 | 不能，容器还没启动 |

### 1.3 创建Docker配置

| 容器 | 用途 | 本机入口 |

#### A.1 APT安装失败（exit code 100）后从哪里继续

**已根据完整失败日志核实的原因（2026-10-21）：**

- 开头`cd: no such file or directory: local-dev`说明目录切换失败，旧命令却继续执行。它不证明整个项目缺少目录；应明确当前工作目录，而非重复`cd local-dev`。新版命令自动识别两个入口，其他位置停止。
- `node:24-bookworm`所有镜像层已下载并解压，`FROM`阶段约1383秒（约23分钟）。不是Node镜像不存在；保留本地缓存，不换Node版本、不清理构建缓存。
- APT阶段约108秒：三个`http://deb.debian.org`索引都报连接失败或超时，目标端口为80。随后APT只发出警告并继续安装，才出现`Unable to locate package chromium`和`fonts-noto-cjk`。**本次是软件索引下载失败，不是包名错误或已证实的磁盘问题。**
- 失败的Dockerfile仍是未换源的旧内容（日志显示285字节，第二行直接执行`apt-get`）。步骤05新版先写入国内HTTPS源，并用`APT::Update::Error-Mode "any"`让索引下载失败直接退出，避免继续报“找不到包”。
- 构建失败后，旧命令又执行`ps`和`exec`，才出现空服务列表及`dev`、`db`未运行。日志未显示pnpm安装或数据库查询成功，不能视为这些步骤已经完成。新版先启动数据库等依赖，构建失败不继续安装项目依赖。

1. 从步骤05复制**完整新版Dockerfile生成命令**执行。源码根目录或`local-dev`均可，它配置了国内Debian/npm源，不影响现有数据卷。
2. 保留已填好的环境参数和步骤06的Compose配置，不要重跑步骤03/04覆盖密码。
3. 紧接着复制下面整段执行，仍可从源码根目录或`local-dev`运行，无须手动切换目录：

```bash
(
set -e
set -o pipefail
if [ -f package.json ] && [ -d local-dev ]; then
  cd local-dev
elif [ "$(basename "$PWD")" = local-dev ] && [ -f ../package.json ]; then
  :
else
  echo '目录不正确：请在源码根目录或其local-dev目录执行。' >&2
  exit 1
fi
printf '本次使用配置目录：%s\n' "$PWD"
docker compose -f compose.yaml --env-file .env config --quiet
docker compose -f compose.yaml --env-file .env up -d db minio mailpit
docker compose -f compose.yaml --env-file .env --progress plain build dev \
  2>&1 | tee dev-build.log
docker compose -f compose.yaml --env-file .env up -d dev
docker compose -f compose.yaml --env-file .env ps
docker compose -f compose.yaml --env-file .env exec dev pnpm install --frozen-lockfile
docker compose -f compose.yaml --env-file .env exec dev pnpm run codegen
docker compose -f compose.yaml --env-file .env exec db \
  psql -P pager=off -U jiedanba -d jiedanba_local -c 'SELECT current_database(), version();'
)
```

预期：三个依赖先启动，开发镜像构建成功后启动`dev`，随后安装项目依赖及生成代码。任一步失败，当前整段即停止；失败前已启动的依赖保持运行，不删卷。更改Dockerfile后正常构建即可，保留已下载的Node层；不要加`--no-cache`、`--pull`或执行`builder prune`强制刷新缓存。括号结束后终端仍在执行前的位置。新日志应显示国内源配置层；如果安装仍请求`deb.debian.org`，先核对实际使用的Dockerfile与构建目录，不继续等相同旧命令重试。

如果仍然失败，在`local-dev`运行`tail -n 100 dev-build.log`，查看`exit code 100`之前的具体错误，不只截取最后的失败总结。`Could not resolve`/`Failed to fetch`/超时属于下载链路；`NO_PUBKEY`/签名错误需核对源和时钟，不能关签名验证；`No space left on device`需检查Docker Desktop磁盘空间，不能用删除数据库卷来处理。需要反馈时提供这些报错行，遮盖其中可能存在的代理凭据。

#### A.2 镜像加速地址403或下载超时

**优先区分：国内镜像加速代理不等于自建镜像仓库。** 本地Docker可以使用服务商提供的国内Docker Hub加速代理，不要求自己先建ACR/TCR仓库、准备联网ECS或购买通用网络代理。前面两个公共地址失败，也不能推断所有国内加速服务都不可用；应依据服务商当前说明验证具体镜像，而非循环猜地址。

**经服务说明核实的候选：毫秒镜像 `docker.1ms.run`。** 参考：https://1ms.run/guide/temp 。文档提供Docker Hub免费加速通道，支持为镜像名添加此前缀。这是第三方加速服务，不是Docker/MinIO官方仓库，企业使用前确认其服务条款、来源可信度及访问限制。后续实际查询原MinIO标签的manifest，认证后返回`MANIFEST_UNKNOWN`；不能再把它当作仅需更换代理即可解决的示例。其他镜像及用户网络仍须逐项验证。

**主路径：配置Docker Desktop全局加速，供本项目及以后Docker Hub拉取复用。**

1. 打开Docker Desktop → Settings → Docker Engine，先保存原JSON配置副本。
2. 仅将`registry-mirrors`字段替换为下面内容，保留其余字段，不重复添加同名字段，也不添加`insecure-registries`：

```json
{
  "registry-mirrors": ["https://docker.1ms.run"]
}
```

上面只演示该字段；如果原JSON还有其他配置，不要用这两行内容覆盖整个配置。移除之前失败的`dockerproxy.com`和`docker.m.daocloud.io`项，先单独验证这个服务。

3. 点击Apply & Restart，等待Docker恢复。重启会中断其他运行容器，事先确认可以重启。
4. 在本地终端检查生效情况，再用原镜像名测试：

```bash
docker info --format '{{json .RegistryConfig.Mirrors}}'
# 此处只验证开发基础镜像的下载，不再重试已撤回的MinIO引用
docker pull node:24-bookworm
```

镜像源输出应包含`https://docker.1ms.run`（可能有末尾斜杠），不能仍是之前的地址。是否能成功下载以这次拉取结果为准；修改成功不等于下载成功。

5. Docker Hub镜像可保留原名及Dockerfile的`FROM node:24-bookworm`，不添加代理前缀。如果已按备选方案加过前缀，可恢复原名；**MinIO保留步骤03用户已验证的华为云SWR完整地址，并配套步骤06的命令/卷**，不恢复已撤回的原引用。完成各镜像拉取验证才能继续步骤07的完整启动命令。基础镜像下载成功不代表MinIO问题解决。

此配置服务于Docker Hub镜像，不是全局网络代理，不会自动加速GHCR、apt或npm。自定义buildx构建器可能需要单独配置镜像源，遇到构建阶段仍直连时要检查具体构建器；不承诺所有构建都自动走此配置。

**备选：仅在不想更改Docker全局配置时使用显式代理前缀。主路径成功后不必执行这一段。** 在本地任意终端只拉取一个具体镜像：

```bash
docker pull docker.1ms.run/library/node:24-bookworm
```

若成功，仅在选择显式前缀备选方案时，将Dockerfile首行改为`FROM docker.1ms.run/library/node:24-bookworm`；它不是MinIO的替代镜像，MinIO仍按步骤03另行解决。

镜像名已明确指定第三方加速域名，不需要自己上传镜像，也不应再请求原来的Docker Hub域名。若仍失败，按代理返回的具体错误检查服务限制或tag，不再推荐它为“已可用”。

其他Docker Hub镜像可按同一规则配置并逐个验证，官方library镜像要带`library/`：

```dotenv
POSTGRES_IMAGE=docker.1ms.run/library/postgres:17-bookworm
MAILPIT_IMAGE=docker.1ms.run/axllent/mailpit:v1.24
NGINX_IMAGE=docker.1ms.run/library/nginx:1.28-bookworm
```

`local-dev/Dockerfile`的首行对应改为`FROM docker.1ms.run/library/node:24-bookworm`，其余内容不变。在`local-dev/`执行`docker compose --env-file .env pull db minio mailpit`，再继续步骤07的构建启动命令；Nginx到步骤13启用时再拉取。镜像加速只处理Docker镜像，Dockerfile里的apt/npm仍有自己的下载地址，不能据此宣称整个离线或国内构建已完成。正式使用应记录并核验镜像摘要，不通过关闭TLS检查绕过错误。

下面保留原镜像加速配置的排查方法；如果上述显式代理前缀已下载成功，无需再为同一镜像切回直连Docker Hub：

如果日志包含`HEAD request to https://docker.m.daocloud.io/...: 403 Forbidden`，失败点是镜像加速服务拒绝请求，尚未运行MinIO。不能据此认定镜像tag不存在，也不是`.env`密码错误。不要删除数据库卷、重建源码或随意换`latest`来处理。

**1. 在本地终端确认当前连接的Docker及镜像源：**

```bash
docker context show
docker info --format '{{json .RegistryConfig.Mirrors}}'
```

**2. 修正对应Docker服务的镜像配置。** 先保存原配置，只移除或替换返回403的那一个地址，不清空其他设置。若是公司统一管理的加速服务，使用公司提供的可访问仓库或让管理员修复授权；不要填来源不明的公共代理。

- Docker Desktop：在Settings → Docker Engine中找到`registry-mirrors`，删除失效的`https://docker.m.daocloud.io`项。仅有这一项时可改为`"registry-mirrors": []`，保留其余JSON配置，再Apply & Restart。
- 自己管理的普通Linux Docker Engine：管理员备份并编辑`/etc/docker/daemon.json`的对应项，然后执行`sudo systemctl restart docker`。rootless或远程Docker须修改实际服务端的配置，不是随意修改本机文件。

重启Docker会中断该Docker上的其他运行容器，先确认没有不能中断的任务。移除镜像源意味着尝试直接连接Docker Hub，**不保证当前国内网络能直连**；如果超时，需要可访问的公司镜像仓库或下面的离线方式，不能用关闭TLS校验解决。

**3. 先单独验证MinIO能下载，再恢复步骤07。** 在本地`local-dev/`目录执行：

```bash
docker compose --env-file .env pull minio
```

仅在`.env`中已填入验证过的MinIO镜像并拉取成功后，重新定义`dc`并从启动这一行继续，不重新生成配置：

```bash
dc() { docker compose --env-file .env "$@"; }
dc up -d --build db minio mailpit dev
dc ps
dc exec dev pnpm install --frozen-lockfile
dc exec dev pnpm run codegen
dc exec db psql -P pager=off -U jiedanba -d jiedanba_local \
  -c 'SELECT current_database(), version();'
```

**4. 不能直连时的备选：** 在公司允许联网的另一台机器拉取相同tag及本机架构的镜像，`docker save`后安全传到本机再`docker load`。示例仅适用于MinIO也运行在amd64的机器；ARM机器使用对应架构，不盲目导入amd64镜像：

```bash
# 可联网机器：填写已经核验来源和架构的镜像，不沿用撤回的地址
read -r -p '输入已核实的MinIO镜像引用：' MINIO_IMAGE
test -n "$MINIO_IMAGE"
docker pull --platform linux/amd64 "$MINIO_IMAGE"
docker save -o minio-image.tar "$MINIO_IMAGE"
# 将tar通过公司批准方式传到开发机，再在开发机执行：
docker load -i minio-image.tar
```

若官方仓库明确返回`manifest unknown`，再核对官方实际可用tag并修改`.env`的`MINIO_IMAGE`；403和连接超时不能作为tag不存在的证据。这里未在用户网络测试任何镜像源。其余镜像、Node基础镜像及Dockerfile构建中的apt/npm下载也需要可用通道，成功导入一个MinIO镜像不代表所有构建依赖都已解决。

**5. 公共加速源失败、官方仓库也超时，而且没有已知可用代理时：停止重复拉取。**

此时先准备下载通道，不继续步骤08，也不删除已经建立的配置或卷。下载渠道是开发环境的前置条件，不能仅靠改Compose参数解决。购买了阿里云ECS不代表它必然能连接Docker Hub；若已有ECS且公司允许作一次性下载准备机，先检查网络，不安装Docker、不部署业务：

```bash
# 在ECS的SSH终端执行，只检查公开地址连通性
curl --connect-timeout 10 --max-time 20 \
  -sS -o /dev/null -w 'Docker registry HTTP=%{http_code}\n' \
  https://registry-1.docker.io/v2/
curl --connect-timeout 10 --max-time 20 \
  -sS -o /dev/null -w 'npm registry HTTP=%{http_code}\n' \
  https://registry.npmjs.org/
```

- Docker registry返回`401`是未认证请求的正常响应，说明此地址初步可达，**不是让用户提供Docker密码**。仍须后续实际拉取来验证认证服务及镜像数据下载域名；只测这个URL不证明镜像能下载。
- npm返回`200`只证明元数据入口初步可达，不证明锁文件中所有tarball、Git依赖或系统包都能下载。
- 返回`000`并超时、DNS或证书错误，表明相应链路还不可用。不要关闭TLS验证；若ECS也不通，就需要公司提供受控代理/内部镜像与包仓库，或由有网络条件的人员准备离线交付包。在这之前本地构建仍被阻塞，不声称“重试即可成功”。

如果准备离线交付，必须一起考虑Compose使用的PostgreSQL、MinIO、Mailpit、Nginx镜像，以及**构建完成的dev镜像**（包含Node、pnpm、Chromium、中文字体）和与锁文件匹配的pnpm依赖缓存。仅`docker save`一个MinIO镜像不足以完成本地开发环境。跨机器时统一CPU架构，校验镜像与文件摘要；离线启动使用已导入的镜像，不再运行依赖联网的`--build`，并验证`pnpm install --offline --frozen-lockfile`能完整成功。以后增加依赖也需要更新缓存或可用包仓库，这个通道要能够长期维护。

## 2. 步骤08：在本地修改对象存储

**在哪里：本地编辑器修改原源码，终端在`local-dev/`。类型：需要开发，不是运行一条迁移命令。**

按下面文件清单接入第1节的MinIO配置；生产选择OSS时保留一个OSS分支。先安装实际选用的SDK：

```bash
# 新终端：先从源码根目录进入local-dev
cd local-dev
dc() { docker compose --env-file .env "$@"; }
dc exec dev pnpm --filter @workspace/api-server add minio
# 仅生产选择阿里OSS时执行；选择其他供应商则使用对应SDK，不全装
dc exec dev pnpm --filter @workspace/api-server add ali-oss
```

SDK安装不会自动替换原代码。完成下面适配后执行`dc exec dev pnpm run typecheck`；步骤11启动后再验证全部上传入口。改动的源码及`package.json`、锁文件属于版本交付，凭据和本地配置不提交。

### 2.1 为什么必须修改

当前 `artifacts/api-server/src/lib/objectStorage.ts` 用的是 GCS SDK，并向 Replit 本机 `127.0.0.1:1106` 取凭据和签名。ECS 上没有这个服务，所以不能只换 bucket 名称。

保持现有上传、预览、下载接口和数据库路径不变，**只换底层存储实现**。这是减少数据清洗和前端改动的关键。

### 2.2 选一种存储，不同时实现三种

| 选择 | 开发采用的 SDK | 要准备的参数 | 说明 |
|---|---|---|---|
| 阿里云 OSS（本文主线） | `ali-oss` | region、bucket、endpoint、访问身份 | ECS/RDS 已在阿里云，接入最直接 |
| 腾讯云 COS | `cos-nodejs-sdk-v5` | region、含APPID的bucket、访问身份 | 同样可用，只改适配层和导入器 |
| MinIO | `minio` 或 S3兼容SDK | endpoint、bucket、访问身份 | 需另外部署MinIO、配置HTTPS、持久磁盘和备份；不要放在临时目录 |

选择 MinIO 不是不能用，但多了一套要维护的存储服务。以下以 OSS 为例；**COS/MinIO 不直接照抄 OSS 的 SDK 代码和 endpoint**。

**本地开发选择：** 第1节已启动MinIO，先实现本地存储分支并接通业务接口。若正式服务也选MinIO，复用同一适配器；若选OSS/COS，生产使用对应SDK分支，本地MinIO测试不能代替云端签名、metadata、ACL和CORS验证，不要求同时实现三家云服务。

本地适配读取第1.3节的`STORAGE_*`变量。`minio:9000`供容器访问，浏览器不能解析这个名字；浏览器PUT URL必须直接按`STORAGE_PUBLIC_ENDPOINT=http://localhost:9000`签发，不能签完后改host。MinIO放行本地`http://localhost:5173`和`http://localhost:8080`所需的PUT/GET/HEAD、Content-Type等头，实测OPTIONS预检。桶保持私有；本地测试统一使用`localhost`，不混用`127.0.0.1`。

### 2.3 需要修改的文件和内容

| 文件 | 具体改动 |
|---|---|
| `artifacts/api-server/src/lib/objectStorage.ts` | 去掉 sidecar/GCS，改为新SDK；实现查找、读取、写入、复制、删除、获取metadata、生成签名URL |
| `artifacts/api-server/src/lib/objectAcl.ts` | GCS `File` 类型和元数据读写改为新存储对应实现；保留原有权限数据，不改变业务角色规则 |
| `artifacts/api-server/src/lib/fileValidation.ts` | 该文件通过GCS对象metadata校验实际大小等信息，改用新适配器；保留原校验规则，不添加新的内容检测要求 |
| `artifacts/api-server/src/routes/storage.ts` | 将GCS文件方法改为适配器方法；保留原路由、返回字段、上传大小限制、文件名与下载行为 |
| `artifacts/api-server/src/lib/uploadSessions.ts` | session字段中GCS路径改为通用对象key；仍使用现有15分钟会话机制，不要求上Redis |
| `lib/object-storage-web/src/use-upload.ts` | 保留“申请URL→PUT→verify”流程，检查新签名URL所需Content-Type和请求头 |
| `artifacts/jiedanba/src/lib/v2api.ts` | 保留 `/api/storage/uploads/direct` 和下载地址拼接，不改业务记录路径 |
| 其他直接调用点 | 搜索 `objectStorageClient`、`getFileFromGCSPath`、`@google-cloud/storage`，逐处替换，不只改上述文件 |

前端头像/账号设置/后台部分页面直接调用上传接口，不都经过共享hook。检查 `Profile.tsx`、`PublisherProfile.tsx`、`AccountSettings.tsx`、`Admin.tsx` 及 `ObjectUploader`，确认请求头、签名PUT、verify与新存储兼容。合同PDF拉取在 `routes/v2/contracts.ts` 有域名限制；若继续使用原同域业务URL通常不用改，若改用新存储直链，就将准确的存储host加入 `ALLOWED_PDF_HOSTS` 并测试签章上传，不要只测浏览器下载。

本地检查直接依赖：

```bash
# 在源码根目录执行，只搜索代码，不读取环境密钥
rg -n 'objectStorageClient|getFileFromGCSPath|@google-cloud/storage|1106|storage.googleapis.com' \
  artifacts/api-server/src lib scripts/src
```

旧迁移脚本仍可留作源端导出用途，不需要把导出器也改成OSS。

### 2.4 固定路径对应关系

建议新桶采用以下 key 布局：

| 旧数据/接口 | 新桶对象key | 用户访问方式 |
|---|---|---|
| DB中的 `/objects/uploads/abc` | `private/uploads/abc` | 仍是 `/api/storage/objects/uploads/abc` |
| 隔离上传对象 | `private/pending/abc` | 不直接提供读取，校验完成后移到uploads |
| 公共根 `public:0` 的 `images/a.png` | `public/0/images/a.png` | 仍是 `/api/storage/public-objects/images/a.png` |
| 公共根 `public:1` 的同名对象 | `public/1/images/a.png` | 按旧公共根顺序查找，保留原先优先级 |

**数据库保存的相对路径不用改。** 适配器负责从业务路径算新桶key，前端不知道底层是OSS、COS还是MinIO。

元数据方面，现有 `custom:aclPolicy` 等字段需要完整保留。不同存储对metadata键名有限制，可以将旧自定义metadata整体JSON编码为base64，存入新metadata字段 `legacy-metadata`；新适配器读取时解码。也可采用等效方案，但**导入器和运行适配器必须使用同一规则**。

桶保持私有，由原有应用接口提供访问，不要为解决预览问题把整个桶改成公共读。现有代码中私有读取的鉴权块有注释，不在迁移时扩大访问范围，也不把重做权限系统作为迁移前提；按原生产实际访问方式做对照测试。

### 2.5 上传方式保持一致

- 普通原始字节上传仍走后端 `/api/storage/uploads/direct`。
- 预签名上传改为新存储的 PUT URL，签名覆盖的 `Content-Type` 必须与浏览器发送一致。
- OSS桶CORS允许原正式域名及临时测试域名的 PUT/GET/HEAD，允许实际上传需要的请求头。完成迁移后删除测试域名。
- API在ECS访问OSS可用内网地址；**发给浏览器的签名URL必须是浏览器可达的HTTPS公网地址**。

## 4. 本地初始化、启动、开发修改与测试

前提：第1节Docker依赖已运行，第2～3节适配完成。这里仅连接本地`db`和本地测试存储，先理解原数据库步骤，再初始化、启动和修改应用。

### 4.1 沿用原来的数据库机制

**新系统安装、恢复系统首次启动、以后版本更新，都沿用当前项目的同一条机制，不另建SQL发布体系：**

```text
当前代码的Drizzle schema
  → build:prod → scripts/migrate.mjs → push-force（同步结构）
  → 启动API → runMigrations（按历史ID执行增量处理）
  → runSeed（按原代码规则检查/补充基础数据）
  → 正常业务与定时任务
```

这些步骤通过 `DATABASE_URL` 连接PostgreSQL，并不必须在Replit运行。本阶段固定连接Docker中的`db:5432/jiedanba_local`；按4.8恢复后仍使用这个库名，不连接在线生产数据库。

`build`只构建代码；`build:prod`才包含原结构同步。本地初次初始化和改schema后均需执行后者，再启动API执行原迁移和seed。

本地验证两件事：空库能初始化；已有测试数据升级后内容仍正确。不更换迁移工具。

### 4.2 本地关闭自动任务，不关闭数据库更新

本地开发和测试保留 `runMigrations()` 和 `runSeed()`，才能验证真实启动效果。为避免自动处理订单/计费，加一个任务开关：

```ts
// 本地需实现；仓库当前没有该开关。保留前面的runMigrations和runSeed调用。
if (process.env.DISABLE_SCHEDULER !== "true") {
  startScheduler();
}
```

本地设置 `DISABLE_SCHEDULER=true`，并隔离真实通知/支付/签章写操作；关闭定时器不等于阻止所有外部副作用。业务任务本身使用测试账号和样例数据单独验证。

**不设置永久跳过初始化的开关，也不删除 `schema_migrations`。** 对恢复库，先在克隆上比较启动前后的数据：原seed有固定账号、配置更新和历史清理逻辑，不能把它当成只读检查；确有不适用于本次部署的内容，只在原seed中做必要调整，不因此废弃整个机制。

原脚本还有一个发布判断问题：`migrate.mjs` 在结构同步失败时可能只打印错误，`index.ts` 在初始化失败后也可能继续监听。沿用时至少要明确检查这些日志，失败停止放流；建议将这些明确失败传为非零退出，使发布脚本停止。这是原流程的错误处理，不是新增迁移体系。`push-force`并不保证只新增，改名、删列、改类型必须按第12节先验证数据影响。

### 4.3 理解本地空库初始化

**这条流程不搬原用户、订单或附件，不能与生产备份恢复流程混用。** 两种起点如下：

| 场景 | 数据库起步方法 | 是否初始化基础数据/管理员 |
|---|---|---|
| 全新独立系统 | 新建空库→build:prod→启动API运行原迁移和seed→验证 | 按原seed初始化，确认符合新系统用途 |
| 现有生产搬迁 | 新建空库→完整恢复备份→核对→运行同一发布流程 | 保留原账号/配置/迁移记录，检查启动逻辑未造成意外变化 |

#### 复用并验证现有初始化机制

**仓库已有建表、增量更新和基础数据初始化能力，并不是缺少初始化机制。** 当前代码的执行链是：

1. API的 `build:prod` 调用 `scripts/migrate.mjs`，通过Drizzle `push-force` 将当前schema同步到数据库。
2. API启动后调用 `runMigrations()`，按 `schema_migrations` 标记执行尚未处理的迁移。
3. 随后调用 `runSeed()`，补账号、角色、智能体配置等数据。

原生产正常运行说明既有部署路径一直在发挥作用。迁往RDS不需要因此另写一套建表系统，也不需要强制改成手工SQL发布。

**尚未验证的只是：当前这份代码从完全空库开始执行，能否完整初始化。** 这里有一个具体的顺序问题需要检查：Drizzle先建出 `demands` 表，而迁移标记表仍为空时，`runMigrations()`会把它识别为旧系统，预填一批历史ID并跳过对应迁移。如果这些迁移的结构和必要初始数据已由当前schema、seed覆盖，就没有缺项；如果未覆盖，就需要补齐那几项。这是需验证的分支，不是已证实的初始化失败。

因此开发首先在隔离空测试库复现上述执行顺序，关闭自动任务及真实外部通知，检查表/字段、必要配置和首个管理员：

- 结果完整：固定已验证的执行步骤，继续用现有代码，不额外制造一套初始化包。
- 确有缺项：只修正空库判断、补漏的初始化步骤，以及新系统不应沿用的固定账号信息；然后从另一空库重新验证。
- `seed.ts`同时含固定账号和历史清理逻辑，新主体安装应先确认哪些内容保留、哪些不适用，不等于全部seed都要重写。
- 不能仅凭API监听成功认定初始化成功：当前入口捕获初始化异常后仍继续服务，需核对初始化日志、SQL检查及业务测试。

登录后检查管理员、基础配置、创建需求/订单、私有与公共附件、头像、模板、下载预览、邮件找回密码、AI流式输出及中文PDF。所有邮件应在Mailpit可见；密码重置链接的地址必须指向本地页面。遇到缺表/字段、默认配置缺失或写入失败，先修原初始化流程再继续，不用手工补库掩盖问题。

### 4.5 步骤12：修改代码并验证修改

### 4.7 步骤14：用本地测试数据演练数据库更新

### 4.10 用数据库终端或桌面客户端连接本地PostgreSQL

#### 方式一：直接进入容器中的psql，不改配置

在`local-dev`目录执行：

```bash
docker compose -f compose.yaml --env-file .env exec db \
  psql -P pager=off -U jiedanba -d jiedanba_local
```

这是交互式SQL终端，出现`jiedanba_local=#`或`jiedanba_local=>`后可输入：

```sql
SELECT current_database();
\dt
\q
```

`\dt`列出表，`\q`退出。不必在宿主机安装PostgreSQL客户端。恢复后仍连接`jiedanba_local`，不需要改库名。

#### 方式二：Navicat、DBeaver、DataGrip等本机客户端

默认Compose没有把数据库端口映射到宿主机。在`local-dev/compose.yaml`里，**只替换`services`下面的`db`服务块**为以下完整内容，其他服务及最底部的`volumes`全部保留：

```yaml
  db:
    image: ${POSTGRES_IMAGE:?set POSTGRES_IMAGE}
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?set POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB:?set POSTGRES_DB}
    ports:
      - "127.0.0.1:15432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 5s
      timeout: 5s
      retries: 20
```

这里新增的是`ports`两行。保留原数据库镜像版本和`pgdata`卷，不换主版本、不删卷。15432是本机端口，容器内部仍是5432；绑定127.0.0.1仅允许本机连接，不开放给局域网或公网。

应用配置会重建db容器，短暂中断数据库连接，先暂停本地读写。在`local-dev`执行：

```bash
docker compose -f compose.yaml --env-file .env config --quiet &&
docker compose -f compose.yaml --env-file .env up -d --no-deps db &&
docker compose -f compose.yaml --env-file .env ps db
```

等待db为healthy，再在客户端新建PostgreSQL连接：

| 参数 | 填写内容 |
|---|---|
| 主机 | `127.0.0.1`，不是容器服务名`db` |
| 端口 | `15432` |
| 用户 | `.env`里的`POSTGRES_USER`，本文默认`jiedanba` |
| 密码 | 初始化本地数据库时使用的`POSTGRES_PASSWORD`，不是网站管理员密码 |
| 数据库 | `jiedanba_local`；初始化和恢复后均使用此名 |
| SSL/SSH | 本地模板未配置，无需启用；此设置不可照搬生产连接 |

API容器仍使用`db:5432`，**不要把`api.env`改成`127.0.0.1:15432`**。若15432被占用，另选空闲本机端口并同步修改客户端。修改`.env`不会自动更改已经初始化的数据库密码，认证失败先核对原密码，不通过删卷解决。桌面客户端只能查看数据库内容，不能查看OSS/MinIO中的附件文件。

## 5. 配置 ECS、RDS、OSS 和生产变量

### 5.1 步骤15：单独整理生产配置

在Replit的Publishing和Secrets/环境配置中核对**生产配置**，通过公司密码管理工具交给服务器管理员，不写入Git、文档或聊天。以下是部署/迁移配置清单，不能复制到第一阶段的本地环境。第二阶段隔离验收优先使用测试配置，第三阶段正式切换再启用原生产身份。

| 配置 | 怎么处理 |
|---|---|
| 生产数据库连接 | 仅用于第三阶段导出；新程序改为RDS连接 |
| `JWT_SECRET` | 原值安全保管，正式迁移保留以维持旧用户令牌；测试环境用独立值 |
| `APP_BASE_URL`、`SITE_URL`、`WEB_ORIGIN` | 正式切换保持原HTTPS域名；隔离验收使用相应测试地址 |
| 腾讯短信四项配置 | 正式迁移保留`TENCENT_SECRET_ID/KEY`、`TENCENT_SMS_APP_ID/SIGN_NAME` |
| 支付两项配置 | 正式迁移保留`PAYMENT_APP_ID`、`PAYMENT_API_SECRET` |
| 电子签章 | 正式迁移保留`ESIGN_APP_ID/SECRET`和生产`ESIGN_BASE_URL` |
| 模型配置 | 原数据库供应商配置在第三阶段随库搬迁；另有`DEEPSEEK_API_KEY`时安全保管 |

### 5.2 步骤16：准备ECS运行环境

主线用 **Ubuntu 24.04 x86_64/glibc + Node 24 + pnpm 10 + Nginx + systemd**。若已买的ECS不是Ubuntu，按其发行版安装同样组件，不必重买服务器。现有依赖裁剪了ARM/musl包，直接用x86_64；不要临时换成ARM或Alpine。

在ECS安装Nginx、Chromium、中文字体和PostgreSQL客户端。以下Ubuntu示例需管理员执行：

```bash
sudo apt-get update
sudo apt-get install -y nginx postgresql-client fonts-noto-cjk ca-certificates unzip nano
```

Node24、pnpm10和Chromium按公司批准的软件源安装；记录实际补丁版本。Ubuntu的Chromium可能由snap提供，安装后用 `command -v chromium` 确认路径并测试服务用户可启动，不假定一定是 `/usr/bin/chromium`。

**在哪里：新ECS的SSH终端，使用具备sudo权限的部署账号。** 以下给出官方Node压缩包安装路径；网络无法访问时，先在公司批准的下载环境取得同名包和官方校验文件再传到ECS，不能从不明镜像拿可执行文件。已有公司管理的Node24时跳过安装，不覆盖它。

```bash
set -euo pipefail
sudo apt-get install -y curl xz-utils snapd
read -r -p '输入已批准的Node24完整版本号（不含v）：' NODE_VERSION
```

### 6.3 步骤21：配置Nginx同时提供前端和API

以下保存为Nginx站点配置（位于 `http` 配置层的include内）。替换域名和证书路径：

**在哪里：ECS终端。** 先将已签发的证书及私钥安全上传至受限临时目录，再安装；不要把私钥放源码或压缩包。下面两处`__...__`替换成上传文件路径：


```nginx
log_format jdb '$time_iso8601 $request_method $uri $status $request_time';
server {
    listen 80;
    server_name app.example.cn;
    return 308 https://app.example.cn$request_uri;
}
server {
    listen 443 ssl;
    server_name app.example.cn;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    root /srv/jiedanba/app/artifacts/jiedanba/dist/public;
    index index.html;
    access_log /var/log/nginx/jiedanba-access.log jdb;
    client_max_body_size 55m;
    client_body_timeout 120s;

    location = /api { return 308 /api/; }
    location ^~ /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        gzip off;
    }
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
    location /assets/ {
        try_files $uri =404;
    }
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

`proxy_pass`末尾不加 `/`，否则可能改掉 `/api` 路径。`proxy_buffering off`用于原有AI流式响应；附件仍经 `/api/storage/...`，不要配置为直接公开整个bucket。

这里是Nginx→本机API一层代理。为保持真实IP/限流效果，在Express配置中增加对本机代理的信任，例如 `app.set("trust proxy", "loopback")`，并确保8080不能绕过Nginx从公网访问；不是无条件信任所有转发头。

```bash
# 仅首次安装：已有同名链接时先核对，不重复创建
sudo ln -s /etc/nginx/sites-available/jiedanba /etc/nginx/sites-enabled/jiedanba
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t`失败不能重载，按其文件/行号修复。

Nginx配置通过后继续下一节启动API，再用测试域名或本地hosts把原域名指到ECS验证，不要修改公众DNS。若用原域名hosts测试，短信/支付平台的服务器回调仍到旧生产，不会跟随你的hosts；完整回调测试使用独立测试回调地址或正式切换后的批准测试单。

### 7.2 步骤24：在Replit备份生产数据库并传输

**在哪里：Replit Shell。已有命令：`pg_dump`、`pg_restore`、`psql`。** 先在ECS由部署账号执行下列目录准备，再回到Replit运行备份代码块：

```bash

```

以下用交互输入避免把连接串写入命令历史；内容不会回显。不要开 `set -x`。备份包含用户和交易数据，放受限目录，下载后及时清除临时副本，不加入Git。

```bash
set -euo pipefail
umask 077
mkdir -p /tmp/jiedanba-export
read -r -s -p '粘贴生产数据库连接串：' PGDATABASE
printf '\n'

  -c 'SELECT current_database();' \
  -c 'SELECT extname, extversion FROM pg_extension ORDER BY extname;'

  --file=/tmp/jiedanba-export/production.dump
pg_restore --list /tmp/jiedanba-export/production.dump \
  > /tmp/jiedanba-export/production.contents.txt

unset PGDATABASE
```

通过批准的SCP/SFTP或受限文件下载方式取走dump和hash；若需Replit文件树下载，临时放入已排除Git的导出目录，下载后删除该临时副本。备份传输使用加密通道，长期留存在公司加密存储中，不放公共下载链接。

**传输命令（Replit Shell）：** 若已批准该环境通过SSH访问ECS，使用受控SSH身份验证，不把私钥粘贴进命令。首次连接核验ECS主机指纹，不使用关闭主机校验的参数。

```bash

  /tmp/jiedanba-export/production.dump.sha256 \
  /tmp/jiedanba-export/production.contents.txt \
  deploy@ECS_HOST:/secure/migration/
```

若Replit没有可用SSH访问权限，则使用受控下载方式先下载到本机，再在本机对这三个文件运行同样的`scp`；无需将生产备份放入源码或提交Git。ECS目录应属于上面实际SSH部署账号，`deploy`不是固定要求的用户名。

**首次在线备份用于试迁；正式切换时停写后再运行一次，得到最终dump。** 不把两份dump混合恢复到同一个库。

现有 `scripts/backup-db.sh` 也能通过 `PROD_DATABASE_URL` 导出gzip SQL，但本文统一custom格式，恢复用 `pg_restore`；两种格式不要混用恢复命令。

## 8. 将数据库恢复到阿里云 RDS

### 8.1 步骤25：准备空恢复库并停止新API

- 在RDS创建**空库**，试迁例如 `jiedanba_trial`，最终迁移另建干净生产库。
- 使用有建表/序列权限的迁移账号恢复；应用账号随后授予需要的表、序列权限。
- 对照源扩展清单确认RDS支持。原库用户/角色不随 `--no-owner --no-acl` 自动恢复，需要映射成RDS账号。
- 新API先停止，不能让它在空库中运行seed或定时任务。

**在哪里：RDS控制台创建库；ECS终端停止服务。** 在RDS控制台选择目标实例的数据库管理，创建新空库及授权账号；此处是新目标，不能选源生产库。操作完成后执行：

```bash
sudo systemctl stop jiedanba-api
if systemctl is-active --quiet jiedanba-api; then
  echo '服务仍在运行，不能恢复'; exit 1
fi
```

### 8.2 步骤26：在ECS配置连接并恢复数据库

将dump放到ECS受限目录 `/secure/migration`。管理员先在受限 `~/.pg_service.conf` 中配置 `jiedanba_restore` 别名，指向新建空RDS库；密码放0600的pgpass文件，TLS参数按RDS证书配置。这样连接串不会出现在命令历史或进程参数中：

**在哪里：ECS终端，用随后执行恢复命令的同一个Linux账号。** 用编辑器打开下列文件；已有其他连接时只追加，不覆盖。下载RDS提供的CA证书到`/secure/migration/rds-ca.pem`：

```bash
umask 077
touch "$HOME/.pg_service.conf" "$HOME/.pgpass"
chmod 600 "$HOME/.pg_service.conf" "$HOME/.pgpass"
# 用本机已安装的编辑器打开两个文件；例如：
nano "$HOME/.pg_service.conf"
nano "$HOME/.pgpass"
```

`.pg_service.conf`追加模板（填实际内网endpoint、库名、用户，不填密码）：

```ini
[jiedanba_restore]
host=__RDS_INTERNAL_ENDPOINT__
port=5432
dbname=__NEW_EMPTY_TARGET_DATABASE__
user=__RDS_RESTORE_USER__
sslmode=verify-full
sslrootcert=/secure/migration/rds-ca.pem
```

`.pgpass`追加一行（五段分别为host、port、dbname、user、password；与上面完全匹配，密码中的冒号及反斜杠按pgpass规则转义）：

```text
__RDS_INTERNAL_ENDPOINT__:5432:__NEW_EMPTY_TARGET_DATABASE__:__RDS_RESTORE_USER__:__PASSWORD__
```

确认文件权限600、证书正确、RDS白名单已放行后执行恢复：

```bash
set -euo pipefail
umask 077
cd /secure/migration
sha256sum -c production.dump.sha256
psql 'service=jiedanba_restore' -X -v ON_ERROR_STOP=1 -c 'SELECT current_database(), inet_server_addr();' \
  -c "SELECT count(*) FROM pg_tables WHERE schemaname='public';"
read -r -p '确认是空目标库，输入 EMPTY_TARGET：' CONFIRM
test "$CONFIRM" = EMPTY_TARGET
pg_restore --no-owner --no-acl --exit-on-error --single-transaction \
  --dbname='service=jiedanba_restore' production.dump
psql 'service=jiedanba_restore' -X -v ON_ERROR_STOP=1 -c 'ANALYZE;'
```

service文件只需按实际连接填写host、port、dbname、user、TLS参数，名称必须与命令中的 `jiedanba_restore` 一致。不要把实际连接串粘到脚本文件。

若恢复报错，保留错误输出，在**另一个新空目标库**重试；不要把 `--clean`、`DROP SCHEMA` 指向源生产库。大型库是否改并行恢复，以试迁耗时决定，不必在第一次搬迁就引入逻辑复制。

### 8.3 步骤27：核对数据库恢复结果

**在哪里：Replit源库和ECS恢复库分别执行；正式对比必须在源库冻结、目标API未启动时。** 把下面代码块保存为受限目录里的`verify-db.sql`，两端使用同一份文件：

```sql
-- 用psql执行；只读，不修改数据
SELECT format('SELECT %L AS table_name, count(*) AS rows FROM %I.%I;',
              schemaname||'.'||tablename, schemaname, tablename)
FROM pg_tables WHERE schemaname='public' ORDER BY tablename
\gexec
SELECT id FROM schema_migrations ORDER BY id;
SELECT conrelid::regclass, conname FROM pg_constraint WHERE NOT convalidated ORDER BY 1, 2;
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid ORDER BY 1;
```

在Replit仍按步骤24安全输入并导出`PGDATABASE`后，执行`psql -X -v ON_ERROR_STOP=1 -At -f /tmp/jiedanba-export/verify-db.sql > /tmp/jiedanba-export/source-check.txt`，随后`unset PGDATABASE`。将`source-check.txt`和`verify-db.sql`一并安全传到ECS的`/secure/migration`。

在ECS执行：

```bash
cd /secure/migration
psql 'service=jiedanba_restore' -X -v ON_ERROR_STOP=1 -At \
  -f verify-db.sql > target-check.txt
diff -u source-check.txt target-check.txt
```

**预期：** 冻结后的表行数、迁移ID一致，约束/索引无新增异常。在线试迁备份后的源库仍会变化，不能用后来查询的源计数宣称备份丢数据；试迁记录时间差，最终以冻结时同一数据版本对账。此步只是基础核对，不能代替下面的金额/字段/序列与内容核验。

同时按实际表字段核对用户、订单、合同、支付/退款、余额/结算、订阅、算力账单：既对数量，也对金额合计、状态、关联ID和关键记录。对全表按主键稳定排序导出并计算内容hash，可发现“数量相同但内容不同”；字段格式、NULL和时区应统一。迁移前没有的数据问题不在这里自行修正。

保留原密码哈希、refresh token表、用户ID和 `schema_migrations`，不要重新创建用户。核对各ID序列的下一值不会与现有最大ID冲突；不要把序列重置成行数。

现有时间字段包含“北京时间数值存入无时区timestamp”的用法，按原值搬迁，不统一加减8小时。订单金额、预算上下限按原值保留，不用旧budget字段重新计算。

## 9. 从 Replit 导出附件并导入新存储

### 9.1 步骤28：在Replit导出存储对象并传输

**在哪里：Replit Shell的源码根目录。** 先确认步骤24、27用的数据库与这里存储属于同一生产环境。导出运行完必须检查失败列表和日志，不只看压缩包存在。

本项目已有源端脚本，**这两条命令可直接用于原存储导出**，但必须先确认Shell中的私有根/公共根对应生产桶，而非测试桶。下载源码并不会下载这些对象。

```bash

pnpm --filter @workspace/scripts exec tsx ./src/export-attachments.ts
```

该命令在scripts包目录执行，生成：

```text
scripts/attachments-export/
  manifest.json
  files/
    private/...
    public_0/...
    public_1/...

```

manifest记录每个文件的组、相对路径、Content-Type、自定义metadata。它不包含全部完整性校验信息，因此导出后补充SHA256；以下在导出目录中生成校验清单，再重新打包：

```bash

  deploy@ECS_HOST:/secure/migration/
```


### 9.2 步骤29：将对象导入目标存储

**现有 `import-attachments.ts` 和 `import-attachments-from-links.ts` 仍写GCS，不能直接写OSS。** 本地适配阶段要一并交付 `scripts/src/import-attachments-oss.ts`，这是本次迁移需要的小工具，不是业务功能升级。

**在哪里：本地先开发并在测试桶验证；交付随步骤19发布到ECS，迁移时只运行它。** 这不是已经存在的可执行脚本。步骤08的开发交付必须包含该导入工具；如果尚未交付，停在这里，不尝试旧GCS导入脚本。脚本读取的目标存储身份、endpoint、bucket与应用适配器保持一致，由运维安全注入；不在命令行传访问密钥。

开发按以下规则实现，避免导入后再大规模清洗：

1. 输入第9.1节解压目录，读取manifest。
2. `group=private` → `private/<relPath>`；`public:0` → `public/0/<relPath>`，依此类推。
3. 上传 `files/<group将冒号改下划线>/<relPath>` 的原始内容；Content-Type和metadata按2.4保留。
4. 大文件使用SDK流式/分片上传，不能一次把所有附件装入内存。
5. 读取上传后的对象，逐项比较SHA256；失败输出清单并返回非零退出状态。仅大小相同不足以跳过。
6. 支持失败重试、已校验对象跳过；遇到未知group直接报错，不回退到第一个公共根。
7. 最终同步能对比源清单与目标：新增上传、同key覆盖更新、源已删除对象列出后同步删除；不要只拷贝新增文件。

```bash
tar -xzf attachments-export.tar.gz -C attachments
cd attachments
sha256sum -c SHA256SUMS
```

开发工具完成后，约定运行命令如下。**该脚本当前不存在，必须在代码适配阶段实际交付并试迁，不能把下面命令视为已经可用：**


如选COS或MinIO，同样交付对应导入脚本，按相同key和metadata规则上传。服务商控制台/`ossutil`/`mc`可用于搬字节，但**只递归复制文件不保证业务metadata被恢复**；若采用CLI，要追加manifest元数据恢复和校验步骤。

## 10. 数据清洗：只修实际变化的路径

**不是“换了存储就必须洗全库”。** 按第2.4节保留业务URL和对象key后，绝大多数相对路径可以原封不动使用。

| 数据内容 | 是否改 | 怎么改 |
|---|---|---|
| `/objects/uploads/...` | 不改 | 新适配器映射到 `private/uploads/...` |
| `/api/storage/objects/...` | 不改 | Nginx继续代理原API |
| 原正式域名下的附件URL | 原域名不变则不改 | DNS切到ECS即可 |
| `storage.googleapis.com/...` 绝对URL | 要处理 | 按源bucket/key映射成稳定的业务URL，不换成新的临时签名链接 |
| `*.replit.app`、旧预览域名绝对URL | 要处理 | 改成原正式域名或相对业务路径 |
| 带签名/到期参数的历史URL | 逐项处理 | 用对应对象业务路径；供应商托管文件则通过其原业务ID重新获取 |
| 富文本、Markdown、JSON中的旧地址 | 要扫描 | 解析相应字段/结构后替换，不对整个数据库文件盲目字符串替换 |
| 旧字体、图片、生成HTML外链 | 实际用到的要处理 | 按3.2迁入国内资源并替换引用 |
| 账号、金额、角色、订单状态、时间 | 不改 | 迁移不是业务数据重算 |

### 步骤31：扫描旧地址，只生成报告

**在哪里：ECS `/secure/migration`，连接已恢复的目标库，API保持停止。配置模板：`scan-old-urls.sql`。** 下列命令创建只读扫描脚本，不输出真实URL、密钥或业务全文，只输出命中的表、列和数量。运行前在脚本的正则中补充现场确认的旧域名；默认规则不是全量外部依赖审计。

```bash
cd /secure/migration
umask 077
cat > scan-old-urls.sql <<'SQL'
\set ON_ERROR_STOP on
BEGIN READ ONLY;
SELECT format(
  'SELECT %L AS table_name, %L AS column_name, count(*) AS matched_rows FROM %I.%I WHERE %I::text ~* %L HAVING count(*) > 0;',
  table_schema||'.'||table_name, column_name,
  table_schema, table_name, column_name,
  'storage[.]googleapis[.]com|[.]replit[.]app|[.]replit[.]dev|[.]repl[.]co'
)
FROM information_schema.columns
WHERE table_schema='public'
  AND data_type IN ('text','character varying','character','json','jsonb')
ORDER BY table_name, ordinal_position
\gexec
COMMIT;
SQL
psql 'service=jiedanba_restore' -X -v ON_ERROR_STOP=1 \
  -f scan-old-urls.sql > old-url-report.txt
```

同时检查manifest和对象内容中的HTML/Markdown引用；数据库扫描不会读取桶内文件。逐项判断“需要替换的旧地址”还是正常历史文本，不对报告结果全部自动替换。

### 步骤32：按确认的映射执行清洗

**在哪里：先在试迁目标库；确认后同一脚本用于最终恢复库。禁止连接源生产。**

开发人员按步骤31结果生成“表、字段、主键、旧值、新值、原因”的映射。新值必须能通过业务接口访问，不能填临时签名URL。JSON/富文本按具体字段结构处理，不能对dump全文替换。未知实际数据之前，不能提供一条安全的“全库自动改地址”命令。

下面给一个**真实字段`users.avatar`的可运行清洗模板**（证据：`lib/db/src/schema/users.ts`），不是所有附件字段的通用脚本。其他命中字段必须各自生成并审阅脚本，保留相同的事务、原值校验和失败退出约束。

在`/secure/migration/avatar-map.csv`中用CSV编辑器填写`user_id,old_url,new_url,reason`四列，首行为列名；只放已确认的头像映射，含逗号/引号的字段按CSV规则转义。不要在文档或聊天贴真实记录。此模板的新地址限定为`/api/storage/`业务路径。

创建`clean-avatars.sql`：

```bash
cd /secure/migration
cat > clean-avatars.sql <<'SQL'
\set ON_ERROR_STOP on
BEGIN;
CREATE TEMP TABLE avatar_map (
  user_id integer PRIMARY KEY,
  old_url text NOT NULL,
  new_url text NOT NULL,
  reason text NOT NULL
) ON COMMIT DROP;
\copy avatar_map FROM 'avatar-map.csv' WITH (FORMAT csv, HEADER true)
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM avatar_map WHERE new_url NOT LIKE '/api/storage/%'
             OR new_url = old_url OR reason = '') THEN
    RAISE EXCEPTION 'Invalid avatar mapping; no changes committed';
  END IF;
  IF EXISTS (
    SELECT 1 FROM avatar_map m LEFT JOIN users u ON u.id = m.user_id
    WHERE u.id IS NULL OR (u.avatar IS DISTINCT FROM m.old_url
                          AND u.avatar IS DISTINCT FROM m.new_url)
  ) THEN
    RAISE EXCEPTION 'Avatar original value mismatch; no changes committed';
  END IF;
END $$;
UPDATE users u SET avatar=m.new_url
FROM avatar_map m WHERE u.id=m.user_id AND u.avatar=m.old_url;
SELECT count(*) AS remaining_mismatches
FROM avatar_map m JOIN users u ON u.id=m.user_id
WHERE u.avatar IS DISTINCT FROM m.new_url;
ROLLBACK;
SQL
chmod 600 avatar-map.csv clean-avatars.sql
psql 'service=jiedanba_restore' -X -v ON_ERROR_STOP=1 \
  -f clean-avatars.sql > clean-avatars-dry-run.txt
```

默认`ROLLBACK`只演练，不保存。核对UPDATE行数与映射数、`remaining_mismatches=0`，并逐个验证新地址的对象存在。审批无误后保存已审阅脚本副本，把**最后一行**改为`COMMIT;`，再用相同命令执行并保存日志。重复执行时已经是新值的记录不会再次更新；任何原值不匹配都会报错回滚。保留映射和清洗前备份，不能只保留清洗后结果。

### 步骤33：清洗后重新核对引用与业务数据

重跑步骤31报告，逐项解释剩余命中；对清洗涉及的每条记录按用户权限访问其对象，确认无404或越权。重做步骤27的数据核验：允许变化仅为批准的URL字段，账号、金额、角色、状态、时间不得变化。桶内HTML等对象若修改了内容，记录修改前后SHA256及原因，不能再要求修改后的对象hash等于原件。

同一份清洗脚本在试迁库和最终恢复库各执行一次，并设计成可重复执行但不会重复改坏值。不要在源生产执行清洗。清洗后检查数据库引用的对象存在，不能只确认bucket里文件数够了。

### 11.1 步骤34：完成一次完整试迁验收

用首次数据库备份和附件导出完成第8～10节，API连接试迁库、禁用定时器、入口限制为测试人员。对照当前生产逐项测试：

| 自动任务 | 在隔离测试数据上核对原自动验收、退款查询、订阅和算力计费，不新增任务规则 |
| 部署 | 深链接刷新无404，服务重启可用，日志无缺文件/依赖错误 |

用国内网络浏览器测试，并确认ECS不再请求Replit sidecar/GCS；替换的服务在原缓存清空后仍能用。记录导出、恢复、附件同步和核对各花多久，据此安排正式维护窗口。

### 11.2 步骤35：维护窗口内重做最终同步并正式切换

1. **提前准备**：确认备案、证书、域名管理权限；降低DNS TTL，例如300秒，并至少等待原TTL周期。保存原解析记录和原生产发布版本。
2. **提前复制附件**：先在线复制大部分对象，减少最后等待时间。需要试迁得到的SHA256/版本清单，最终仍要处理覆盖和删除。
3. **通知短时维护**：期间不能发布需求、下单、上传等；目标是搬完后效果一致，不虚称维护期间完全无感。
4. **停止旧生产写入**：在Replit Publishing中停止/关闭已发布生产应用；**不是只按工作区Stop按钮**。检查并停掉任何连接生产库的工作区API、定时任务及脚本。此时只保留必要导出权限。
5. **处理正在发生的操作**：等原上传完成或取消，并等已发出的上传签名过期及在途写入结束，避免停API后还有直传文件变化。现有签名通常15分钟，实际窗口按在途完成情况确认。
6. **处理支付/签章回调**：维护前记录未完成支付、退款和签署单。按现有供应商重试与查单机制，在恢复后核对补齐；确认其重试覆盖维护时间。若不覆盖，就不能直接停掉回调入口，要保留能可靠处理的单一回调入口并等其写入结束再取最终快照，或改期安排窗口。不要求为本次迁移新建消息平台，但不能漏掉已付款/已签事件。
7. **最终备份数据库**：重新执行第7节。核实旧库确实不再变化，再导入新建的空正式RDS库，不能继续使用试迁时产生测试数据的库。
8. **最终同步附件**：重扫源对象，补新增/覆盖、处理删除；校验SHA256和引用。执行已在试迁验证的清洗脚本。
9. **核对并执行已演练的发布流程**：先确认恢复后的表计数、关键字段、资金、合同、附件、水位一致，再执行 `build:prod` 并在入口关闭、任务禁用条件下启动原迁移/seed，核对变化仅为试迁确认的预期内容。原 `last_billed_at` 等计费字段原样保留，避免重复或漏算；失败不进入切换。
10. **切原域名到ECS**：证书和Nginx已准备好。旧API保持停机，新环境使用正式库；取消新环境 `DISABLE_SCHEDULER`，只运行这一份生产任务。
11. **恢复访问**：启动服务，验证登录、历史数据、新上传、通知、支付与签章回调；对维护期在途订单主动查单/核对，不手工重复扣款。
12. **观察并保留旧备份**：DNS缓存可能让部分用户短时仍到旧地址；此时旧端只能停止/维护或转发到新端，不能重新用旧库营业。确认无问题后再关旧资源，按公司保留周期保留备份。

Replit关闭生产应用的具体入口以当前Publishing界面为准；关闭应用不等于删除数据库或项目。**不要关闭源数据库或删除存储**，否则最后备份无法执行。把发布改Private也不能代替停任务，它只限制访问。

### 11.3 登录“无感”需要保留什么

保留原正式域名/HTTPS origin、`JWT_SECRET`、用户密码哈希、refresh token表，用户原浏览器localStorage中的令牌才可能继续使用。现有访问令牌2小时、刷新令牌7天；已过期的不会因迁移复活。

短信验证码和上传session在内存中，重启后会丢；维护期间的验证码需重发、未完成文件可能需重传。不为这些短期状态强制升级Redis。若更换正式域名，浏览器localStorage不跨域，需重新登录，所以主线保留原域名。

### 11.4 失败时怎么退

- **新系统还没接收真实写入**：停止新服务，恢复原域名解析及旧生产；补核对维护期支付/签章事件。旧数据仍是权威源。
- **新系统已经有真实新订单/付款/附件**：先停新写入。优先修新环境或回退程序版本但继续用新数据库/存储；若必须回旧环境，要先把新期间的数据和附件完整带回并对账，再恢复服务。**不能直接改DNS指回旧库，否则会丢刚产生的数据。**

不在迁移当天销毁旧库和备份，也不让两端同时跑自动任务。

# 附录：后续版本开发与数据库更新

## 12. 本地开发、测试通过后再发布生产

**不论是全新初始化的系统，还是从生产备份恢复的系统，以后都用同一套更新流程。** 搬到RDS以后，Replit的发布不会替国内RDS更新表结构。

### 12.1 本地开发与线上数据库如何分工

准备三个互不混用的数据库连接：

| 数据库 | 用途 | 数据处理规则 |
|---|---|---|
| 本地开发库 | 写代码、调整Drizzle定义、调试 | 只放测试数据或获准脱敏数据，可以重建 |
| 发布测试库 | 从同版本基线或受控备份恢复，试跑本次更新 | 验证旧数据升级；不开真实自动任务/通知 |
| RDS生产库 | 用户正式使用 | 按原schema同步、迁移和seed更新，不能拿本地库覆盖 |

开发机的 `DATABASE_URL` 默认只连本地库，生产凭据只用于批准的运维操作。不因开发方便把应用连接直接指向生产。**发布的是代码和数据库差异，不是把本地整个数据库重新导入生产。**

### 12.2 本地开发继续改原来的文件

| 修改内容 | 继续修改的位置 | 发布时如何生效 |
|---|---|---|
| 新表、新字段、索引等结构 | `lib/db/src/schema/` | 原 `build:prod` 中的Drizzle同步 |
| 旧业务数据回填、特定一次性处理 | `artifacts/api-server/src/lib/migrations.ts` | 按原 `once(id, ...)` 和 `schema_migrations` 执行 |
| 默认配置、基础数据 | `artifacts/api-server/src/lib/seed.ts` | 按原存在检查/版本判断更新，避免覆盖运营配置 |
| 使用新字段的功能 | 对应前后端业务代码 | 构建并重启后生效 |

仍按原约定给新迁移唯一ID，不修改已执行迁移的含义，不删除历史标记来强行重跑。修复已上线迁移应加新ID。恢复生产备份时必须带上原 `schema_migrations`，否则会失去这些判断依据。

例如增加订单可选字段：改schema及业务代码，在本地运行结构同步；若需要给旧订单计算初值，再在原 `migrations.ts` 增加一次性回填。**不用为了迁到RDS额外制作另一份SQL发布包。** 代码与这些数据库定义/迁移一起提交Git、一起发布。

### 12.3 发布前验证原流程，而不是换流程

在一份旧版本测试库上运行新版本的 `build:prod`，再启动新API，测试新增字段与旧数据读取。测试库来自初始化后的旧版本或受控备份，不是在已经手改成新结构的库上假测升级；自动任务和真实外部通知按第4.2节隔离。

重点检查：

- 新字段是否真的存在，历史订单/金额/账号是否保留，迁移ID是否正确记录。
- seed重复执行是否只产生预期变化，而非覆盖运营配置或固定账号误清理。
- 再次启动是否不会重复扣数据/回填；现有迁移执行与写标记不保证全部在同一事务，可能中途失败的处理须可重试，不能假定所有步骤自动回滚。
- 构建、结构同步、启动迁移、seed四个阶段分别确认成功，不能只看最后HTTP 200。

普通新增字段可按原流程处理。**改名、删表/列、改类型、增加非空/唯一约束**需要先检查旧数据和Drizzle输出：`push-force`会自动接受部分破坏性变更，并不等于只增不删。如果测试显示会误删再建，针对这个变更在原发布流程中增加明确的数据保留步骤或分版本发布，不能在生产直接试。这是任何数据库更新都要处理的内容，不是RDS特有问题。

### 12.4 ECS/RDS正式发布顺序

1. 上传与测试一致的新版本源码，安装锁定依赖，执行第6.1节预构建检查，保留旧版本目录。
2. 记录目标数据库、代码版本及当前迁移记录，先完成RDS备份。
3. 本手册采用维护窗口：停业务写入和API任务，按第11节处理在途支付/签章。避免旧API仍运行时新构建已经修改表结构。
4. 在新版本目录运行**原生产构建命令**。它会连接RDS同步结构，因此此时才提供正确的 `DATABASE_URL`：

```bash
# ECS新版本源码根目录；连接串安全输入，不从systemd env文件直接source
set -euo pipefail
read -r -s -p '输入已备份的目标RDS连接串：' DATABASE_URL
printf '\n'
export DATABASE_URL
PGDATABASE="$DATABASE_URL" psql -X -v ON_ERROR_STOP=1 \
  -c 'SELECT current_database(), inet_server_addr();'
read -r -p '确认目标库及备份，输入 RELEASE_CONFIRMED：' CONFIRM
test "$CONFIRM" = RELEASE_CONFIRMED
NODE_ENV=production pnpm --filter @workspace/api-server run build:prod
unset DATABASE_URL
# 必须检查结构同步日志成功；原migrate.mjs可能吞掉失败，不能只看shell退出码。
```

5. 确认同步成功才将systemd的应用路径切到新版本，执行 `daemon-reload`（unit变更时）和 `restart jiedanba-api`。由原启动代码执行 `runMigrations()`、`runSeed()`；不要永久跳过它们，也不要同时启动两份API执行迁移。
6. 用 `journalctl -u jiedanba-api` 查看这次启动日志，核对新迁移ID、关键配置及业务数据；失败保持维护。入口不放流，直到初始化和关键业务测试通过。
7. 验证原账号登录、旧订单读取、本次新功能写入和任务状态，恢复访问。

API启动期间仍需对应DDL/DML权限；若构建使用不同数据库账号，两者必须指向同一库，并保证建出的对象对API可用。只有代码变化时仍可采用同一发布命令，schema无差异不应产生结构变化；也可在明确无数据库变更时仅build并重启，不能漏掉实际需要的结构同步。

### 12.5 更新失败怎么办

- 构建/结构同步失败：不启动新版本；检查数据库实际状态，不能假定 `push-force` 或跨多个迁移全部自动回滚。
- 启动迁移/seed失败：保持维护，按具体错误修复原逻辑后重试，保留已完成标记；不要清空标记表。
- 数据库已更新、新代码失败：旧代码兼容新结构时可以回退代码，仍用当前库；不兼容则修复或按已演练方案恢复。
- 开放写入后出现问题：先停写并保护新数据，不能直接用发布前备份覆盖新订单。

**统一流程：本地改原schema/迁移/seed及业务代码→在旧库副本试跑原发布流程→备份RDS→build:prod同步结构→启动执行原迁移/seed→验收。新装和恢复来的系统都这样更新。**

日常用RDS自动备份，并确认一次可以恢复；附件使用所选存储的备份/版本保留，MinIO则另做持久数据备份。保留API和Nginx日志并轮转，原业务任务仍由单API运行即可。

### 12.6 以后每次发布的完整操作单（不再打开Replit）

以下是日常更新，**不是重做步骤23～33的数据搬迁**。线上用户/订单仍保留在当前RDS和存储中。首次部署后，代码由本地和公司Git仓库管理；后续按以下顺序发布。

**A. 本地开发与验证**

1. 从公司Git仓库取得代码或更新本地分支，检查`git status`，不要覆盖未提交修改。
2. 用步骤07启动本地Docker依赖，按步骤12修改源码。
3. 执行步骤11～14：类型检查、空库/旧测试库更新验证、前后端功能与构建测试。
4. 提交改动并推送公司Git仓库，记录提交号。按步骤19的`git archive`打包，传到ECS `/tmp/jiedanba-update.zip`。每次都打包新提交，不重复用第一次下载的ZIP。

**B. ECS准备新版本目录，先不接生产数据库**

```bash
set -euo pipefail
read -r -p '输入本次提交号（仅字母数字短横线）：' RELEASE_ID
[[ "$RELEASE_ID" =~ ^[A-Za-z0-9-]+$ ]]
RELEASE_DIR="/srv/jiedanba/releases/$RELEASE_ID"
test ! -e "$RELEASE_DIR"
sudo install -d -m 755 /srv/jiedanba/releases
sudo install -d -o "$(id -un)" -g "$(id -gn)" -m 755 "$RELEASE_DIR"
unzip /tmp/jiedanba-update.zip -d "$RELEASE_DIR"
cd "$RELEASE_DIR"
unset DATABASE_URL
export PUPPETEER_SKIP_DOWNLOAD=true
pnpm install --frozen-lockfile
pnpm run codegen
pnpm run typecheck
pnpm --filter @workspace/api-server run build
NODE_ENV=production BASE_PATH=/ pnpm --filter @workspace/jiedanba run build
test -s artifacts/api-server/dist/index.mjs
test -s artifacts/jiedanba/dist/public/index.html
test -s artifacts/api-server/dist/assets/fonts/NotoSansSC.otf
```

**C. 维护、备份、原机制更新**

在发布账号的`.pg_service.conf`和`.pgpass`中按步骤26另配`jiedanba_prod`，明确指向当前正式RDS，不能误用试迁库。先安排维护、处理在途支付/签章回调，再停API及所有外部写入者。以下命令仍在同一个ECS终端执行：

```bash
sudo systemctl stop jiedanba-api
if systemctl is-active --quiet jiedanba-api; then exit 1; fi
umask 077
BACKUP_DIR="/secure/migration/release-$RELEASE_ID"
mkdir "$BACKUP_DIR"
psql 'service=jiedanba_prod' -X -v ON_ERROR_STOP=1 \
  -c 'SELECT current_database(), inet_server_addr();'
read -r -p '确认正式库及全局停写，输入 BACKUP_CONFIRMED：' CONFIRM
test "$CONFIRM" = BACKUP_CONFIRMED
pg_dump --dbname='service=jiedanba_prod' -Fc --no-owner --no-acl \
  -f "$BACKUP_DIR/before-update.dump"
pg_restore --list "$BACKUP_DIR/before-update.dump" > "$BACKUP_DIR/contents.txt"
sha256sum "$BACKUP_DIR/before-update.dump" > "$BACKUP_DIR/before-update.sha256"
```

备份成功后，在`$RELEASE_DIR`执行第12.4节的原`build:prod`命令，安全输入**同一个正式库**连接，检查结构同步成功。失败停在维护状态，不执行下面切换。API环境文件保留正式RDS、存储和原JWT，检查本次是否新增配置，不能用本地`api.env`覆盖它。

**D. 切换程序目录并启动**

首次部署的`/srv/jiedanba/app`是实目录；第一次更新将它保留后改为指向版本目录的链接。后续更新同样保留旧链接。以下命令只移动程序目录/链接，不移动数据库和存储；执行前确认上一阶段成功。

```bash
cd "$RELEASE_DIR"
sudo chgrp -R jiedanba artifacts/api-server/dist
sudo chmod -R g+rwX artifacts/api-server/dist
OLD_PATH="/srv/jiedanba/releases/previous-$(date +%Y%m%d%H%M%S)"
test ! -e "$OLD_PATH"
sudo mv /srv/jiedanba/app "$OLD_PATH"
sudo ln -s "$RELEASE_DIR" /srv/jiedanba/app
sudo systemctl start jiedanba-api
sudo systemctl status jiedanba-api --no-pager
sudo journalctl -u jiedanba-api -n 100 --no-pager
curl --fail http://127.0.0.1:8080/api/healthz
sudo nginx -t
sudo systemctl reload nginx
```

服务仍通过原`/srv/jiedanba/app`路径读取代码，Nginx也读取该路径下的新前端。启动按原机制执行迁移和seed；检查日志、旧账号/订单、新功能及任务状态后再结束维护。健康接口200不能代替业务验证。数据库若已变化，程序回退遵循第12.5节兼容性条件，不直接回灌旧备份。

### 12.7 完全退出Replit的检查与日常维护

1. **源码**：本地和公司代码仓库有完整版本与锁文件，能从一次全新检出重建Docker开发环境，不需要Replit注入变量。
2. **运行**：国内API、附件、邮件及实际使用的AI/工具路径不请求Replit sidecar、旧对象托管或旧预览域名；按第3节处理剩余境外服务。不只是改掉首页域名。
3. **发布**：按12.6完成一次独立更新演练，前端产物、API、原数据库更新和进程重启均在本地/ECS完成，不点击Replit Publish。
4. **任务**：只保留国内生产的一份业务调度器。原Replit的数据库备份工作流不再运行；在RDS控制台开启符合原保留要求的自动备份并实际恢复到独立测试库验证。对象存储同样配置备份/版本保留；自建MinIO必须另外备份卷中对象及metadata，不能把容器卷视为备份。
5. **运维命令**：ECS通过`sudo systemctl status jiedanba-api --no-pager`、`sudo journalctl -u jiedanba-api --since today`、`sudo nginx -t`及供应商监控检查服务、磁盘、证书到期、备份结果；不要依赖Replit日志面板。
6. **退役**：确认新生产数据对账完成、业务稳定、回滚窗口结束及备份已独立保存后，停止旧发布/定时任务，再撤销旧环境凭据和访问权限。先停服务再逐项处理保留数据，不直接删除旧库/对象来“验证独立性”。
