# 模型路线、容量规划、BOM 与部署拓扑

> 本章提供与具体厂商、型号和价格无关的规划方法。公式用于售前初估和候选方案比较；最终配置必须使用目标模型、目标推理引擎、真实业务样本和候选硬件压测校准。

## 1. 规划假设与计量口径

计算前冻结下列输入；任一项变化都应重新估算并判断是否需要复测。

| 类别 | 必填输入 |
|---|---|
| 模型 | 参数量 `P`、层数 `L`、注意力头数、KV 头数 `H_kv`、头维度 `D_head`、权重与 KV 精度、模型许可 |
| 请求 | 输入 Token 的 P50/P95/P99、输出 Token 的 P50/P95/P99、峰值请求率、并发会话、流式/非流式、超时率 |
| SLA | 首 Token 时延 TTFT、单 Token 时延 TPOT、端到端时延、可用性、降级目标、恢复时间 RTO、恢复点 RPO |
| 引擎 | 推理引擎及版本、张量/流水线并行度、连续批处理、Paged KV、前缀缓存、投机解码 |
| 环境 | 加速器软件栈、CPU 架构、机房供电与制冷、联网限制、国产化要求 |
| 余量 | 业务增长、故障接管、碎片、发布双版本及维护窗口余量 |

统一使用二进制容量（GiB、TiB）或十进制容量（GB、TB），不得混算。换算关系为：

```text
1 GiB = 2^30 Byte
1 GB  = 10^9 Byte
```

建议容量表同时保留“理论值、实测值、规划值”三列，并注明每个系数的来源和核验日期。

## 2. 模型路线及边界

| 路线 | 适用条件 | 主要成本或风险 | 不应选择或升级条件 |
|---|---|---|---|
| 原精度直接推理 | 质量优先、容量充足，需要最小化转换风险 | 权重和通信开销最大 | 资源无法满足 SLA 或单位吞吐不可接受时转量化 |
| 量化推理 | 已有质量基线，希望降低显存、功耗或提升吞吐 | 算子兼容、质量回退、量化校准成本 | 核心任务质量下降超过验收阈值；硬件无高效量化算子 |
| RAG | 知识更新频繁、需引用溯源、知识可文档化 | 检索质量、权限穿透、索引更新与存储 | 问题主要是行为或格式学习而非知识缺失；不得用 RAG 绕过数据授权 |
| LoRA/QLoRA | 需稳定风格、术语或任务行为，数据规模有限 | 数据治理、训练与版本管理 | RAG 或提示工程已达标；缺少高质量训练与评测集 |
| 持续预训练 | 领域语料充足且通用模型领域能力明显不足 | 算力、数据版权、灾难性遗忘 | 无可证明收益或无持续训练运维能力 |
| 全量训练/微调 | 有独特数据壁垒、成熟算法团队和长期预算 | 最高算力、存储、网络和治理成本 | 一般企业知识助手默认不进入此路线 |
| 多模态模型 | 业务确有图像、音频或视频输入 | 编解码、预处理、显存和网络波动大 | 纯文本任务不因“能力更全”而默认选择 |

推荐升级顺序：

```text
提示与流程基线
  → RAG
  → 量化或推理优化
  → 参数高效微调
  → 持续预训练或全量路线
```

每次升级必须由可复现的质量或 SLA 缺口触发，而不是由模型规模触发。RAG、微调和量化解决的是不同问题，不能互相替代：

- 知识缺失或更新快：优先 RAG。
- 输出行为、格式、风格不稳定：在评测证明提示工程不足后考虑微调。
- 质量已达标但资源不足：考虑量化、蒸馏、调度或并行优化。
- 基座领域能力不足且有合规语料及成熟团队：才评估持续预训练。

### 2.1 按任务选择模型角色

| 角色 | 必测维度 | 选型重点 | 常见误区 |
|---|---|---|---|
| 通用对话/生成 | 指令遵循、事实性、拒答、目标语言、长上下文、工具调用 | 用客户任务集比较质量、TTFT、TPOT、吞吐和许可 | 只看参数量或公开总榜 |
| 代码 | 目标语言/框架、仓库上下文、编译/测试通过率、安全缺陷 | 用客户允许的脱敏代码任务测试补全、修改、解释和工具调用 | 用自然语言评分代替可执行测试 |
| 视觉/多模态 | OCR、图表、页面、分辨率、图片数、视频/音频预处理 | 同时计算视觉 Token、预处理时延、显存和隐私边界 | 纯文本场景为“能力更全”而选多模态 |
| Embedding | 目标语言、专业术语、长短文本、向量维度、归一化、最大输入、批吞吐 | 用标注 query-document 集测 Recall@K/MRR/nDCG；确认向量库距离函数、维度和模型许可 | 只看通用排行榜；换模型后复用旧索引 |
| Rerank | 候选长度、语言、领域、Top-K、截断、单对/批处理时延 | 在固定初检候选上比较 nDCG/MRR、P95 时延和吞吐；验证交叉编码器或生成式重排的资源成本 | 用重排替代 ACL；Top-K 无上限拖垮时延 |

### 2.2 Embedding 与 Rerank 决策流程

1. 从真实查询抽取训练集外的黄金集，至少包含相关、不相关、同义表达、专业缩写、时间敏感和越权文档。
2. 固定文档解析、切分和初检候选，分别比较候选 Embedding；不得同时更换切分器后宣称提升来自模型。
3. 记录模型版本、Tokenizer、向量维度、是否归一化、距离函数、最大输入、截断方式、批大小、索引参数和硬件。
4. Embedding 放行至少看 `Recall@K、MRR/nDCG、P95 编码时延、批吞吐、索引体积、许可`；跨语言场景必须按语言分桶。
5. 只有初检能召回正确文档但排序不佳时才加入 Rerank；放行看固定候选集上的质量增益是否覆盖 P95 时延和资源成本。
6. ACL 必须在可证明安全的检索阶段强制执行。Rerank 输入不得包含调用者无权查看的候选文档。
7. 更换 Embedding、维度、归一化或距离函数时创建新索引并灰度，禁止在旧索引中混写；保留旧索引直到回退窗口结束。

## 3. 可复算容量公式

### 3.1 权重显存

设参数量为 `P`，权重位宽为 `b_w`：

```text
M_weight_raw(Byte) = P × b_w / 8

M_weight_plan = M_weight_raw × (1 + α_quant + α_runtime)
```

- `α_quant`：量化比例尺、零点、分组元数据等开销。
- `α_runtime`：权重对齐、额外张量、引擎加载等开销。
- 两个系数不得永久沿用经验值，应通过模型加载后的显存实测反推。
- 多卡张量并行时，权重可近似除以并行度，但嵌入层、输出层、缓存和工作区通常不会完全均分。
- 某些量化方案并非所有参数均使用同一位宽，应按各参数组分别求和。

### 3.2 KV Cache

对常见自回归 Transformer，单 Token、单序列 KV 容量近似为：

```text
KV_token(Byte) = 2 × L × H_kv × D_head × b_kv / 8

KV_total = KV_token × ΣS_i × F_beam × (1 + α_page)
```

其中：

- `2` 表示 Key 与 Value。
- `L` 为 Transformer 层数。
- `H_kv` 必须使用 KV 头数；GQA/MQA 不可误用查询头数。
- `D_head` 为每个头的维度。
- `b_kv` 为 KV Cache 位宽。
- `S_i` 是第 `i` 个驻留序列当前已占用 Token 数，包含已缓存的输入和输出。
- `F_beam` 是 beam search、多候选或并行采样放大系数；普通单候选解码取 `1`。
- `α_page` 是分页、块未填满、碎片和前缀缓存保留开销。

对混合注意力、滑动窗口、状态空间或特殊缓存模型，应依据模型配置和引擎实现替换本公式。规划时至少计算以下场景：

1. 日常请求长度分布；
2. P95 长度与峰值并发同时出现；
3. 最大上下文全部打满的保护场景。

不能简单用“最大上下文 × 最大并发”作为日常采购值，也不能只用平均长度作为生产上限。

### 3.3 激活、工作区与总显存

```text
M_total =
    M_weight_plan
  + M_KV
  + M_activation
  + M_workspace
  + M_graph
  + M_reserved

M_total ≤ M_accelerator_aggregate × U_mem_target
```

- `M_activation` 随 prefill 批量、序列长度、并行策略变化。
- `M_workspace` 与算子、量化内核、通信库有关。
- `M_graph` 为图捕获或多个 batch shape 预留。
- `M_reserved` 包括驱动上下文、碎片和突发保护余量。
- `U_mem_target` 不应取 `100%`，应为运行时碎片、突发长请求和升级双版本保留空间。

激活和工作区难以仅凭模型结构准确预测。初算可设置明确标注的暂定值，但采购前必须以目标引擎的以下四组数据替换：

1. 空载加载；
2. 短请求；
3. 最大 prefill；
4. 最大 decode 批次。

### 3.4 并发、批处理与吞吐

并发必须拆分为：

- 已接入并发；
- 等待队列；
- prefill 活跃序列；
- decode 活跃序列；
- KV 驻留序列。

连续批处理下，配置的最大 batch 不等于每轮有效 batch。容量估算公式为：

```text
Token_demand = λ_peak × (T_in + T_out)

N_capacity = ceil(Token_demand / (Q_measured × U_slo))

N_final = max(N_capacity, N_HA, N_maintenance)
```

- `λ_peak`：峰值请求数/秒。
- `T_in`、`T_out`：与压测场景匹配的平均输入、输出 Token；正式压测应采用分桶分布而非单一平均值。
- `Q_measured`：单个部署单元在满足 TTFT/TPOT 条件下的实测 Token/s，而非厂商理论峰值。
- `U_slo`：扣除抖动、排队、增长余量后的目标利用率系数。
- `N_HA`：满足约定故障接管目标所需的最少部署单元数。
- `N_maintenance`：滚动升级或维护时满足服务目标所需的最少部署单元数。

若 prefill 与 decode 的瓶颈不同，应分别核算两阶段容量并取较大值。批处理增大通常提高总吞吐，却可能恶化 TTFT/TPOT；优化目标应是“满足 SLA 下的最大稳定吞吐”，而不是单独追求加速器利用率。

### 3.5 主存与存储

```text
RAM_plan ≥
    OS与守护进程
  + 引擎CPU开销
  + 权重暂存或卸载
  + RAG缓存
  + 峰值余量

Disk_plan ≥
    Σ(模型版本 × 权重及分词器)
  + 镜像和软件包
  + 索引
  + 日志
  + 检查点
  + 回滚版本
  + 备份暂存
```

补充约束：

- 模型转换和量化时，源格式、目标格式与临时文件可能同时存在。
- 滚动升级至少允许当前版与候选版并存。
- RAG 原文、向量、倒排索引、元数据和备份应分别估算；副本不是备份。
- 训练场景还需加入优化器状态、梯度、激活、数据集和多个检查点，不能套用推理公式。

## 4. 容量计算示例

以下仅演示计算过程，不代表推荐模型或硬件。假设一个自回归模型及业务具有下列参数：

| 参数 | 示例值 |
|---|---:|
| 参数量 `P` | 320 亿 |
| 权重位宽 `b_w` | 4 bit |
| 层数 `L` | 64 |
| KV 头数 `H_kv` | 8 |
| 头维度 `D_head` | 128 |
| KV 位宽 `b_kv` | 16 bit |
| KV 驻留序列数 | 24 |
| 每序列平均已占用 Token `S` | 4,096 |
| `F_beam` | 1 |
| KV 分页与碎片系数 `α_page` | 10% |
| 权重量化与运行时附加系数之和 | 12% |
| 激活、工作区、图和保留空间暂定值 | 10 GiB |
| 目标显存利用率 `U_mem_target` | 85% |

### 4.1 权重

```text
M_weight_raw
= 32,000,000,000 × 4 / 8
= 16,000,000,000 Byte
≈ 14.90 GiB

M_weight_plan
= 14.90 × (1 + 0.12)
≈ 16.69 GiB
```

### 4.2 KV Cache

```text
KV_token
= 2 × 64 × 8 × 128 × 16 / 8
= 262,144 Byte
= 0.25 MiB

ΣS_i
= 24 × 4,096
= 98,304 Token

KV_total_raw
= 0.25 MiB × 98,304
= 24 GiB

KV_total_plan
= 24 × (1 + 0.10)
= 26.4 GiB
```

### 4.3 总显存

```text
M_total
= 16.69 + 26.4 + 10
= 53.09 GiB
```

若候选部署单元的聚合可用显存为 `80 GiB`：

```text
M_safe
= 80 × 0.85
= 68 GiB

53.09 GiB ≤ 68 GiB
```

因此该候选方案在本组假设下理论上满足显存安全线，但仍须验证多卡切分是否均衡、单卡峰值是否越界，以及最大 prefill 时的工作区是否超过暂定值。这里的 `80 GiB` 仅是算例中的聚合容量，不指向任何固定型号。

### 4.4 吞吐与副本数

继续假设：

| 参数 | 示例值 |
|---|---:|
| 峰值请求率 `λ_peak` | 1.5 请求/秒 |
| 平均输入 `T_in` | 3,000 Token |
| 平均输出 `T_out` | 500 Token |
| 满足 SLA 时单部署单元实测 `Q_measured` | 2,200 Token/秒 |
| `U_slo` | 70% |

```text
Token_demand
= 1.5 × (3,000 + 500)
= 5,250 Token/秒

单部署单元规划吞吐
= 2,200 × 0.70
= 1,540 Token/秒

N_capacity
= ceil(5,250 / 1,540)
= 4
```

若 HA 和维护要求均未高于 `4` 个部署单元，则 `N_final = 4`。若要求任一部署单元故障后仍承载完整峰值，则还应执行 N-1 校验：

```text
(N_final - 1) × 1,540 ≥ 5,250
```

本例中 `3 × 1,540 = 4,620`，不满足完整峰值接管，因此应增加部署单元、提升单元实测吞吐，或书面约定故障时的降级 SLA。该例也说明“有多个副本”不等于“满足 HA 容量”。

## 5. 小、中、大可替换 BOM

以下是能力档和采购约束，不是唯一型号清单。满足接口、容量、兼容性、可靠性和实测 SLA 的部件均可替换。

| 档位 | 典型目标 | 加速计算能力 | CPU/RAM 能力 | 本地与共享存储能力 | 网络能力 | 冗余边界 |
|---|---|---|---|---|---|---|
| 小型 | PoC、开发、部门级低并发；可接受计划停机 | 单节点、少量加速器；总显存覆盖权重、KV、工作区和安全余量 | CPU 满足分词、预处理及数据供给；RAM 覆盖模型加载和服务开销 | 企业级 NVMe，容纳双模型版本、镜像、临时转换文件和日志；备份到节点外 | 双端口业务网；独立带外管理 | PoC 可单机；生产使用时至少采用冗余电源、系统盘保护和外部备份 |
| 中型 | 企业生产、多租户、中等并发 | 至少两个独立推理副本；副本内可使用多加速器高速互联 | 每节点 CPU、RAM、PCIe 通道不超配；NUMA 与卡拓扑匹配 | 本地高速模型缓存，加独立共享制品仓库与备份存储 | 业务、存储、管理分区；双网卡、双上联 | 失去一个副本或节点后仍满足书面降级 SLA；支持负载均衡和滚动升级 |
| 大型 | 高并发、长上下文、多模型或严格 SLA | 多节点资源池；按模型选择独立副本、张量并行或流水线并行；保留故障接管容量 | 高 I/O 平台；按 NUMA 绑定；控制面与数据面资源隔离 | 分层存储、模型仓库、索引集群及独立备份域；满足并发冷启动和恢复窗口 | 业务与管理双上联；跨节点并行采用独立低时延通信平面；可采用双交换平面 | N+1 或故障后容量冗余；网关、控制面、存储元数据多副本；按业务要求评估同城灾备 |

### 5.1 每档 BOM 的能力项

实际 BOM 至少包含以下类别和能力描述：

1. **计算节点**：可容纳的加速器数量、单节点聚合显存、内存带宽、PCIe 通道、NUMA 拓扑。
2. **加速器**：目标精度算子支持、显存容量和带宽、卡间互联、ECC 和故障遥测。
3. **CPU 与 RAM**：分词、预处理、RAG、模型加载和故障转储所需能力。
4. **本地盘**：系统盘保护、模型缓存、临时转换空间、写入耐久度。
5. **共享存储**：模型制品、索引、日志、检查点和备份恢复能力。
6. **网络**：业务、存储、跨节点通信、管理和带外管理端口及交换能力。
7. **机架设施**：双电源、双 PDU、UPS 接入、机柜承重、导轨、线缆和气流组织。
8. **运维能力**：带外管理、固件升级、硬件遥测、备件和维保响应。

### 5.2 可替换性验收清单

替换任一加速器或服务器平台前，必须核验：

1. 权重与 KV 位宽、目标算子、量化格式是否原生支持。
2. 驱动、固件、内核、容器运行时、编排插件、通信库和推理引擎版本矩阵。
3. 单卡显存、内存带宽、卡间互联、PCIe 通道与 NUMA 拓扑。
4. ECC、故障遥测、带外管理、固件升级和备件服务能力。
5. 在同一数据集、同一 SLA、同一功耗上限下比较吞吐和稳定性。
6. 模型许可证、软件许可证、密码能力及国产化或行业合规要求。

## 6. 网络、功耗、散热与冗余

### 6.1 网络

网络至少区分以下四类流量：

1. 业务接入；
2. 集群通信；
3. 存储与备份；
4. 管理与带外管理。

可物理隔离，也可在风险评估后逻辑隔离。

- 单节点或独立副本：业务网主要由请求、流式输出和 RAG 数据决定。
- 跨节点张量/流水线并行：主要瓶颈变为每步 collective 或点对点通信，必须用目标并行策略实测。
- 存储网：按模型冷启动、并发拉取、索引构建及备份窗口倒推。

```text
BW_required =
    Peak_payload
  / Target_utilization
  × Protocol_overhead
  × Burst_factor
```

各系数含义：

- `Peak_payload`：业务、通信或存储在目标时间窗内的峰值有效载荷。
- `Target_utilization`：允许的链路目标利用率，小于 `1`。
- `Protocol_overhead`：封装、重传和通信库附加系数，大于或等于 `1`。
- `Burst_factor`：微突发与流量不均衡系数，大于或等于 `1`。

生产环境建议双网卡、双上联接入不同交换故障域。大规模集群使用双交换平面时，应实际演练单链路、单交换机和拥塞故障。不得以端口标称速率替代端到端有效吞吐。

### 6.2 功耗与散热

```text
P_IT_peak =
    Σ(节点峰值功耗)
  + 网络设备峰值功耗
  + 存储设备峰值功耗
  + 管理设备峰值功耗

P_feed_plan =
    P_IT_peak
  × Growth_factor
  / Redundancy_derating

Heat_IT(kW) ≈ P_IT(kW)

Heat_IT(BTU/h) ≈ P_IT(W) × 3.412

Facility_power ≈ P_IT × PUE
```

- 峰值功耗应取设备功率上限与实测压力峰值中的较安全者，并加入启动瞬态。
- `Growth_factor` 覆盖约定周期内扩容。
- `Redundancy_derating` 反映某一路退出后其余供电路径的可承载比例，具体取值由机房专业方确认。
- 核查机柜总功率、单路支路电流、三相平衡、插头/PDU 制式和降额要求。
- 双电源只有接入不同 PDU 和不同支路才形成冗余。
- UPS、发电机和制冷冗余必须由机房专业方确认。
- 高密度机柜应核验进出风方向、冷热通道、回风温度、压差和热点，不能只看机房总冷量。
- 容量验收应在接近规划功率的持续负载下测量温度、降频、风扇、PDU 和 UPS 指标。

## 7. 拓扑与高可用

| 拓扑 | 优点 | 故障域与限制 | 适用条件 |
|---|---|---|---|
| 单工作站或塔式 | 成本与操作复杂度低 | 主机、卡、电源均可能成为单点 | PoC、开发、非关键业务 |
| 单生产节点多卡 | 卡间通信简单、时延低 | 节点故障导致服务中断 | 允许停机或有外部降级渠道 |
| 多个独立副本 | 横向扩展、故障隔离、升级容易 | 单副本必须能装下模型；需设计会话和缓存策略 | 优先推荐的生产形态 |
| 单副本跨多节点并行 | 可承载单节点放不下的模型 | 任一参与节点或链路故障影响整个副本 | 模型容量确实要求跨节点 |
| 编排平台资源池 | 多租户、调度、滚动升级与自动恢复 | 控制面和运维复杂度较高 | 多模型、多团队、持续扩缩容 |

生产 HA 最低闭环：

1. 两个以上独立服务副本跨节点或机架故障域部署。
2. 网关健康检查同时覆盖进程存活、模型就绪和小请求可用。
3. 故障后剩余容量满足约定的降级 SLA，而不只是“仍有实例在线”。
4. 模型权重、配置、密钥和索引可从受控仓库重建；缓存不作为唯一数据源。
5. 控制面、网关、DNS/NTP、制品仓库、向量库元数据和监控链路应识别并消除单点。
6. 明确有状态会话的粘性、KV 丢失行为、请求重试幂等和流式中断语义。
7. 定期演练节点、加速器、网卡、交换机、存储和可用区故障，并记录 RTO/RPO。

### 7.1 HA 容量校验

对要求失去 `F` 个部署单元后仍满足降级吞吐 `D_degraded` 的集群：

```text
(N_final - F) × Q_measured × U_slo ≥ D_degraded
```

还需同时验证故障状态下的 KV 容量、队列长度、TTFT/TPOT 和入口限流。若不能满足，应在合同和运行手册中明确自动降级措施，例如降低最大上下文、限制低优先级租户、暂停批量任务或转入经批准的备用服务。

## 8. 压测校准方法

1. **冻结版本**：记录模型哈希、量化产物、驱动和固件、引擎、容器、内核参数及并行策略。
2. **建立请求分桶**：按短、中、长输入，短、长输出，RAG/非 RAG，多租户及突发流量构造真实比例；数据必须脱敏且经授权。
3. **分层测试**：依次测试单请求基线、固定并发阶梯、突发、最大上下文、混合流量、故障接管和长稳。
4. **同时采集**：TTFT、TPOT、P50/P95/P99 时延、请求和 Token 吞吐、队列、拒绝率、显存/KV 使用、功耗、温度、降频、网络和存储吞吐。
5. **寻找 SLA 拐点**：逐级提高负载，直到首次违反任一 SLA；前一稳定档位作为实测容量上限。
6. **回填系数**：用实测反推量化开销、KV 分页浪费、工作区、有效 batch、目标利用率和单副本吞吐，替换初始假设。
7. **长稳与故障测试**：在规划负载持续运行，并执行单副本退出、链路中断和滚动升级；验证无 OOM、无持续泄漏且接管容量达标。
8. **形成证据**：保存压测工具版本、原始结果、监控导出、配置、异常和复测记录。

出现以下变化时重新校准：

- 模型、量化格式或上下文策略变化；
- 推理引擎、驱动、固件或通信库升级；
- 加速器、CPU、内存、网络或存储平台替换；
- 并行策略、批处理、KV Cache 或调度参数变化；
- 请求长度分布、并发、租户组合或 SLA 明显变化。

## 9. 扩容触发条件

扩容采用“多指标、持续窗口、预测提前量”，避免因单次尖峰采购。具体阈值和观察窗口由业务方与运维方共同确认。

### 9.1 立即扩容或限流评审

- P95/P99 TTFT、TPOT 或端到端时延在连续观察窗口违反 SLO，且应用异常和可优化项已经排除。
- 正常流量下持续排队、拒绝或超时；故障接管后无法满足降级 SLA。
- KV 或总显存高水位持续逼近安全线，出现 OOM、频繁驱逐或长上下文无法准入。
- 加速器已处于吞吐拐点，增加并发只增加时延而不增加有效吞吐。
- 网络、存储、CPU、RAM、功率或温度先于加速器饱和。

### 9.2 计划性扩容

- 基于增长预测，预计在“采购交付周期 + 安装验收周期 + 安全缓冲期”内耗尽容量余量。
- 新模型、新租户、上下文增长、双版本发布或 RAG 索引增长将突破现有预算。
- 维护或任一约定故障域退出时，剩余资源不能承载约定负载。
- 机柜电力、制冷、网络端口、地址、许可证或存储达到规划水位；此类扩容通常应早于计算资源采购。

### 9.3 优先优化而非扩容

- 低利用率但高时延：先检查排队策略、CPU 预处理、NUMA、网络、存储和冷启动。
- KV 浪费严重：先评估长度分桶、准入控制、Paged KV、前缀缓存及上下文上限。
- 小请求批处理不足：先调整连续批处理、调度和副本负载均衡。
- 质量允许：评估更小模型、蒸馏或量化，但必须重跑质量验收。

## 10. 方案交付标注要求

每份容量和 BOM 方案必须附带：

- 假设日期；
- 模型、软件和固件版本；
- 公式输入及单位；
- 理论值、实测值和规划值；
- 目标 SLA 与业务流量分布；
- 每项余量的用途；
- 故障接管能力与降级边界；
- 未验证项和风险责任人；
- 替代部件的最低能力门槛；
- 重新压测的触发条件。

价格、交期、具体型号和兼容状态属于时效性信息，应在采购前依据官方资料和授权供应渠道另行核验，不写入长期有效的方法论基线。
