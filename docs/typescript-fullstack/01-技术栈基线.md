# 01｜技术栈基线与选型边界

> 适用基线：截至 **2026-08**。本文刻意记录“发布线与升级政策”，不锁定容易过期的补丁号。开始前先读[总览](./00-手册总览.md)，工程落地见[工程规范](./02-工程规范.md)，质量门禁见[质量、安全与可观测性](./03-质量安全与可观测性.md)。

## 1. 结论先行

TypeScript 全栈项目起步采用：

- 一个 `pnpm` workspace Monorepo；
- 一个 React + Vite 单页应用（SPA）；
- 一个 NestJS 模块化单体 API；
- PostgreSQL；
- 共享“契约”，不共享服务端实体和 ORM 类型；
- TypeScript 全仓严格模式；
- Docker 用于可重复交付，但**不起步使用微服务、Kubernetes、事件溯源**。

Next.js 是第二阶段必须掌握的 React Web 框架，但不是因为“TypeScript 全栈就必须 Next.js”。只有 SSR、流式服务端渲染、搜索引擎收录、内容路由或前端侧 BFF 的收益明确时才引入。

## 2. 版本策略

### 2.1 版本选择规则

每次初始化或季度升级时执行以下规则，而不是从本文复制补丁号：

1. Node.js 选择官方仍处于 Active LTS 或 Maintenance LTS 的偶数主版本；新项目优先当时的 Active LTS。
2. TypeScript、pnpm、React、Vite 选择当前稳定发布线；不使用 beta、RC、nightly。
3. NestJS 与 Next.js 选择当前稳定主版本，确认 Node.js 支持矩阵，再由 lockfile 固化实际版本。
4. PostgreSQL 选择官方仍受支持、托管平台可用且 ORM 驱动已验证的稳定主版本。
5. 工具链在 `package.json` 声明 Node/pnpm 约束，以 Corepack 固定 pnpm，在根 lockfile 固化全部传递依赖。
6. 同一变更只跨一个主版本；先读迁移指南，在独立 PR 中升级并运行全门禁。
7. 安全修复可越过季度节奏；框架主版本不得由自动依赖机器人直接合并。

“当前稳定”指官方标记为 stable/latest 且已满足本仓验证矩阵，不等于发布当天无评估追新。

### 2.2 手册基线矩阵

以下是 **2026-08-27 新建演练仓库的开工基线**。表中补丁号用于留下可复核起点；初始化时必须写入 `packageManager`、`engines` 和 lockfile，之后只能按升级流程变更。不得把 `latest` 范围写进依赖声明。

| 层次 | 开工版本 | 用途与约束 |
|---|---|---|
| 运行时 | Node.js `24.x` LTS（核验时 24.19.0） | 本地、CI、容器必须同一主版本；不依赖实验 API |
| 语言 | TypeScript `7.0.x`（核验时 7.0.2） | 全仓 `strict`；应用不直接执行 TS，由框架/构建器编译 |
| 包管理 | pnpm `11.x`（核验时 11.24.0）+ Corepack | 唯一 lockfile；CI 使用 frozen lockfile |
| 浏览器应用 | React `19.2.x` + Vite `8.2.x` | 默认后台、交互型工作台和 SPA |
| API | NestJS `12.0.x` | 模块化单体、REST/OpenAPI、后台任务入口 |
| React Web 框架 | Next.js `16.3.x` | 第二阶段专项；有 SSR/RSC/SEO 等明确需求时单独建 app |
| 数据库 | PostgreSQL `18.x`（核验时 18.6） | 生产使用托管实例或独立持久化卷 |
| ORM | Prisma `7.10.x` | 本演练唯一 ORM；使用 Prisma Migrate，不用 `db push` 代替共享环境迁移 |
| 运行时校验 | Zod `4.4.x` | 外部输入必须运行时校验；Nest 边界通过适配 Pipe 复用 schema |
| API 描述 | OpenAPI 3.x | API 是契约源时生成客户端；不得手抄重复 DTO |
| 单元/组件测试 | Vitest `4.1.x` + React Testing Library | 测行为，不测私有实现 |
| API 集成测试 | Nest 测试工具 + HTTP 测试客户端 | 使用真实 PostgreSQL 隔离实例 |
| 端到端 | Playwright `1.62.x` | 少量关键用户旅程 |
| 静态质量 | ESLint + Prettier | 规则集中管理，CI 零 warning |
| 可观测性 | OpenTelemetry + 结构化日志 | 遵循开放协议，避免业务代码绑定单一厂商 |

版本证据来自 Node.js 官方发布页、PostgreSQL 官方发布页和 npm registry 的 stable/latest 标签；Prisma 的 `latest` 在核验日指向 8.0 RC，因此刻意选择其稳定发布线 `7.10.x`，不把预发布版纳入基线。精确解析结果由 M0 首次 lockfile 固化。

### 2.3 升级台账

仓库必须维护以下机器可读事实：

- 根 `package.json`：`packageManager`、`engines.node`；
- 根 lockfile：精确依赖解析；
- CI 镜像与生产镜像：相同 Node 主版本；
- Renovate/Dependabot：补丁/次版本分组，主版本单独 PR；
- ADR：ORM、认证、Next.js 引入等不可逆或高成本决策；
- 每季度检查 EOL、漏洞、迁移指南和浏览器支持范围。

## 3. React + Vite、NestJS、Next.js 的职责

### 3.1 React + Vite：默认前端

负责浏览器 UI、客户端路由、交互状态、表单与 API 调用。适合：

- 登录后的管理后台和协作工作台；
- 搜索引擎收录不是核心要求；
- 已有独立 NestJS API；
- 需要清晰学习浏览器、React 生命周期和 HTTP 边界。

Vite 是开发服务器与前端构建器，不是后端框架。SPA 静态产物可由 CDN/Nginx 托管，业务规则仍留在 API。

### 3.2 NestJS：默认主后端

负责身份边界、授权、用例编排、领域规则、事务、持久化、外部集成和后台任务：

- Module 类似组合根/功能模块，不等于 DDD 限界上下文；
- Controller 只做协议适配；
- Provider 是依赖注入注册单元，不代表所有类都应是 Service；
- Guard 适合认证与粗粒度授权，资源级授权仍需应用层根据已加载资源判断；
- Pipe/运行时 schema 负责边界校验，TypeScript 类型不能替代它。

起步只部署一个 API 进程。模块边界先在代码和数据访问中建立，不能为了“未来扩展”先拆网络边界。

### 3.3 Next.js：有证据才引入

Next.js 负责 React 的服务端渲染、静态生成、React Server Components、内容路由与前端聚合。适合：

- 公开营销站、文档站、内容详情页有 SEO 指标；
- 首屏性能必须通过服务端数据获取改善；
- 需要按路由选择静态、动态或流式渲染；
- 团队能承担服务器/边缘运行时、缓存失效和 hydration 的复杂度。

边界规则：

- Next.js **不与 NestJS 同层替代**：前者首先是 React Web 框架，后者是通用后端应用框架。
- 已有复杂业务 API 时，Next.js Route Handler 仅做 UI 聚合、会话适配或安全代理，不复制领域逻辑。
- 小型内容型产品可仅用 Next.js；当后台任务、复杂授权、跨渠道 API、长事务或独立扩缩容出现时，再引入 NestJS。
- 同一页面不要无理由在浏览器、Next.js BFF、NestJS 之间形成三跳链路。

### 3.4 决策表

| 问题 | 选择 |
|---|---|
| 内部系统/登录后 SPA，已有 API | React + Vite + NestJS |
| 公开内容强 SEO，同时有复杂业务域 | Next.js + NestJS |
| 小型内容/表单产品，后端很薄 | 可仅 Next.js，记录 ADR |
| 多客户端、后台任务、复杂事务 | NestJS 作为主后端 |
| 只是希望“前后端都用 TS” | 不是引入 Next.js 的理由 |

默认学习顺序：现代 JavaScript/TypeScript → 浏览器与 React → Vite SPA → NestJS API/PostgreSQL → 契约与测试 → Next.js 对比实践。

## 4. pnpm Monorepo 基线

建议目录（名称表达职责，不要求复制空目录）：

```text
apps/
  web/                 # React + Vite
  api/                 # NestJS 模块化单体
  web-next/            # 第二阶段且有明确场景时才创建
packages/
  contracts/           # 可跨进程传输的 schema、DTO、错误码
  ui/                  # 无业务规则的 UI 基础组件
  config-eslint/       # 共享静态规则
  config-typescript/   # 共享 tsconfig 基线
  test-support/        # 测试工厂与基础设施，不进生产运行时
tooling/
  scripts/             # 仓库级可重复脚本
```

### 4.1 依赖方向

- `apps/web` → `packages/contracts`、`packages/ui`；
- `apps/api` → `packages/contracts`，但领域层不依赖传输 DTO；
- `packages/contracts` 不依赖任何 app、ORM、NestJS 或 React；
- `packages/ui` 不访问数据库，不导入服务端环境变量；
- app 之间禁止源码级相互 import，只通过已发布的 HTTP/队列契约通信；
- 共享包必须有真实复用者；“可能以后复用”不足以抽包。

使用 pnpm workspace protocol 表达内部依赖。根脚本统一 `lint`、`typecheck`、`test`、`build`，任务编排器只有在构建耗时有数据支持时才引入。不要把 Monorepo 等同于微服务。

### 4.2 TypeScript 编译边界

- 基础配置开启 `strict`、`noUncheckedIndexedAccess`、`useUnknownInCatchVariables`；
- 各 app 明确浏览器/Node 环境，不把 DOM 类型泄漏到后端；
- 不用 path alias 跨越包的 `exports`；
- 生产包只导出公开入口，禁止引用其他包内部路径；
- 禁止大面积 `any`、`@ts-ignore`；例外要带原因、范围和移除条件。

## 5. 数据与契约默认选型

### 5.1 PostgreSQL 与 ORM

默认 PostgreSQL，因为其事务、约束、索引、JSON 和运维生态足以覆盖起步阶段。业务不应依赖 ORM 隐式同步 schema；结构变化只通过可审查迁移。

本演练固定使用 **Prisma 7.10.x + Prisma Migrate**，避免后续编码任务在 ORM 和迁移机制上分叉。其他项目可通过 ADR 选择 Drizzle：适合 SQL 能力成熟、希望 schema 更贴近 TypeScript/SQL，且愿意自行建立仓储与迁移约束的团队。

不要同时使用两套 ORM。复杂查询允许使用参数化 SQL，但必须有集成测试和执行计划审查；HTTP DTO 不得直接暴露 Prisma 生成类型。

### 5.2 共享契约

推荐“schema-first 的共享包”或“OpenAPI-first + 生成客户端”二选一，细则见[工程规范：共享契约](./02-工程规范.md#5-共享契约与-api)。无论哪种方式：

- 网络输入都要运行时验证；
- 日期、金额、ID 在传输层使用明确字符串格式；
- ORM 模型、领域实体不能发布给前端；
- 契约变更必须兼容或有版本迁移计划。

## 6. TypeScript 全栈运行边界

| 边界 | 核心规则 |
|---|---|
| Node.js + V8 | 事件循环适合 I/O；CPU 密集工作放入 Worker 或独立后台作业 |
| TypeScript | 多数类型在运行时擦除；外部输入必须通过运行时 schema 校验 |
| pnpm workspace | lockfile 必须提交；同仓不等于共享一切或部署在同一进程 |
| NestJS DI | 只注册需要生命周期或基础设施注入的对象；纯领域对象直接构造 |
| Prisma | 持久化模型不直接作为 HTTP DTO；事务上下文必须显式传递 |
| React | 浏览器状态、渲染和副作用边界清晰；不能承担服务端授权 |
| Next.js | 明确 build、server、client、edge 的执行位置及秘密边界 |
| AsyncLocalStorage | 可传播 request/trace 上下文，但不能替代显式租户和权限参数 |

## 7. 明确不做

起步阶段禁止：

- 按技术层或“将来高并发”拆微服务；
- 引入 Kubernetes、服务网格、分布式事务；
- 用事件溯源作为主数据模型；
- 为简单 CRUD 建立完整战术 DDD 对象图；
- 同时引入 Redux、多个服务端状态库和多个表单库；
- 让浏览器直接持有数据库、AI 提供商或对象存储密钥；
- 用 Next.js 重写已稳定的 NestJS 领域逻辑。

出现下列证据后才评估升级：独立团队所有权、明确扩缩容差异、部署节奏冲突、法规隔离、单体边界无法控制，且模块化、索引、缓存和后台作业优化均已验证不足。升级提案必须有指标、ADR、回滚方案和总拥有成本。

- [ ] TypeScript 严格选项、ESLint、Prettier 在根规则中统一。
- [ ] PostgreSQL schema 由迁移创建，不使用生产自动同步。

- [ ] 未引入微服务、Kubernetes、事件溯源。
- [ ] 依赖方向和公开包入口由 lint/构建检查。
