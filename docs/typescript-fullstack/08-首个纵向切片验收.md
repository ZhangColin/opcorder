# 08｜M0–M1 首个纵向切片编码与验收规格

> 导航：[返回手册首页](./00-手册总览.md)｜[项目规格](./06-实战项目规格.md)｜[全部手写里程碑](./07-手写里程碑.md)

本文是后续编码任务的输入，不提供业务源码。关键字“必须/不得”是硬性门禁。实现可在不改变行为的前提下调整命名，但须同步契约、迁移和本文的追踪表。

## 1. 固定架构约束

- 单一 pnpm workspace；至少包含 `apps/web`、`apps/api`，M0 不创建 worker。
- Web 是 React + Vite SPA；API 是 NestJS 模块化单体；数据存储是 PostgreSQL。
- M1 只新增 `identity` 与 `tenancy-access` 业务模块。模块内部按 domain/application/infrastructure/interface 分责，但不强制每层一个目录。
- HTTP 契约可由共享 schema 包生成/复用；禁止共享 ORM entity、Repository、Nest provider 或 React 组件。
- 一次请求只能通过应用服务进入领域/数据层；Controller 不写 SQL、不直接调用 ORM。
- 不引入微服务、消息代理、Kubernetes、事件溯源、外部 RBAC 服务、Redis 会话或第三方身份平台。

### 1.1 开工锁定表

M0 按[技术栈基线](./01-技术栈基线.md#22-手册基线矩阵)开工：Node.js 24.x LTS、pnpm 11.x、TypeScript 7.0.x、React 19.2.x、Vite 8.2.x、NestJS 12.0.x、PostgreSQL 18.x、Prisma 7.10.x、Zod 4.4.x、Vitest 4.1.x、Playwright 1.62.x。初始化当天将精确版本写入 `packageManager`、`engines` 和 lockfile；若任一组合无法通过引擎/peer dependency 验证，先提交 ADR 调整基线，不得静默换栈。

M0–M1 的唯一数据路径是 Prisma Client + Prisma Migrate；不安装第二套 ORM，不以 `db push` 代替迁移。M0–M2 不创建 Worker；M3 才按[里程碑](./07-手写里程碑.md)引入同代码库 Worker。

## 2. 全局接口约定

API 前缀为 `/api/v1`。JSON 使用 camelCase。时间为 UTC ISO 8601。成功创建返回 `201`，无响应体的成功操作返回 `204`。

错误体固定字段：

| 字段 | 规则 |
|---|---|
| `code` | 稳定、可供前端分支的机器码，如 `VALIDATION_ERROR` |
| `message` | 面向用户/开发者的安全描述，不含堆栈和 SQL |
| `requestId` | 与响应头 `X-Request-Id` 一致 |
| `details` | 可选；校验错误仅给字段与原因 |

认证失败返回 `401`；已认证但缺少组织级能力返回 `403`；按 ID 访问其他租户对象返回 `404`；唯一性/并发冲突返回 `409`；字段校验返回 `400`；限流返回 `429`。所有端点拒绝 schema 未声明字段。

列表即使 M1 数据少也不得无限返回：`limit` 默认 20、最大 100；按稳定字段排序；M1 可使用 offset，M2 起改游标。

## 3. M0：可重复工程骨架

### 3.1 编码任务顺序

| 顺序 | 任务 | 可观察完成条件 |
|---:|---|---|
| 0.1 | 初始化 workspace 和 Node/pnpm 版本约束 | 根命令可递归执行，错误版本快速失败 |
| 0.2 | 创建最小 Web/API 与共享契约包 | 依赖方向通过 lint 规则或边界测试约束 |
| 0.3 | 配置 format、lint、TypeScript strict、测试 | 单独命令与根聚合命令均存在 |
| 0.4 | 实现环境 schema | 缺少/错误变量时启动失败且列出变量名，不打印值 |
| 0.5 | 接 PostgreSQL 和迁移 runner | 空库 upgrade 成功；再次执行无变更 |
| 0.6 | 实现日志、request id 和错误过滤器 | 任一响应可关联一条结构化请求日志 |
| 0.7 | 实现健康与版本端点 | 满足 3.2 契约 |
| 0.8 | Web 实现 API 状态页 | loading、ready、error 可测试 |
| 0.9 | 加测试与 CI | 干净环境从安装到构建/测试/迁移验证一次通过 |

不得调换 0.4–0.7：先建立启动失败和错误可见性，再增加 UI。

### 3.2 M0 HTTP 契约

| 方法与路径 | 认证 | 响应 |
|---|---|---|
| `GET /health/live` | 否 | `200 {"status":"ok"}`；不查询数据库 |
| `GET /health/ready` | 否 | 数据库可用且迁移状态可接受时 `200 {"status":"ready","checks":{"database":"up"}}`；否则 `503` |
| `GET /version` | 否 | `200`，含非空 `version`、`commit`、`builtAt`；不得含环境变量 |

健康端点不得输出数据库地址、凭据或异常堆栈。版本值从构建元数据注入；本地可使用明确的 `dev`，不得伪造提交号。

### 3.3 M0 配置最低集

必须校验运行环境、HTTP 端口、数据库 URL、允许的 Web origin、日志级别、session secret（M0 可未消费但生产环境必须强度校验）、构建版本。测试使用独立数据库；不得自动连接开发或生产数据库。仓库只提交变量名和安全示例。

### 3.4 M0 测试与验收

- **单元**：环境 schema 对缺失、类型错误、生产弱 secret 失败；错误映射保持稳定 code。
- **集成**：真实 PostgreSQL 上空库迁移、重复迁移；ready 在数据库可用/不可用两种响应。
- **前端**：状态页三态；错误态可重试；不可访问 API 时不伪装成功。
- **E2E smoke**：浏览器打开 Web，看到 ready 和版本；API 未就绪时看到明确错误。
- **静态门禁**：strict 类型检查、lint、format check、build 无错误；生产依赖高危漏洞有处置记录。

M0 验收脚本按以下顺序执行并保存命令与结果：干净安装 → 启动依赖 → 迁移 → 静态门禁 → 测试 → 构建 → smoke → 停止依赖。主代理负责实际运行；编码任务不得通过修改测试来掩盖失败。

## 4. M1：账号、组织与 RBAC

### 4.1 M1 范围

M1 必须完成：

1. 邮箱密码注册、登录、查看本人、退出全部会话；
2. 登录用户创建和列出自己的组织；
3. 通过路径中的 organization id 进入组织并列出成员；
4. `OWNER` 创建邀请，未注册或已注册用户都可接受；
5. 接受后成为 `MEMBER`；重复/过期/撤销邀请失败；
6. 对组织端点实施 membership 与角色授权；
7. 记录注册、登录成功/失败、退出、创建组织、创建/接受邀请的审计。

M1 不做邮箱真实投递、忘记密码、邮箱验证、SSO/MFA、修改角色、移除成员、所有权转移、工作空间或计费。开发环境只在响应/受保护调试界面展示一次邀请接受 URL；生产环境在未配置邮件前必须显式禁用邀请创建，不能静默丢弃。

### 4.2 数据模型与硬约束

实现必须通过迁移得到等价结构：

| 表 | 必需字段（除通用时间字段） | 必需约束/索引 |
|---|---|---|
| `users` | id, email, normalized_email, display_name, status | normalized_email 全局唯一；status 初始 `ACTIVE` |
| `credentials` | user_id, password_hash, password_changed_at | user_id 主键/唯一；不存明文/可逆密码 |
| `sessions` | id, user_id, token_hash, csrf_token_hash, expires_at, revoked_at, last_seen_at | token_hash 唯一；按 user/有效期索引 |
| `organizations` | id, slug, name, created_by | slug 全局唯一；名称非空 |
| `memberships` | id, organization_id, user_id, role, status | `(organization_id,user_id)` 唯一；role 限 `OWNER/ADMIN/MEMBER` |
| `invitations` | id, organization_id, normalized_email, role, status, token_hash, expires_at, accepted_at, revoked_at, invited_by | token_hash 唯一；`status=PENDING` 时以部分唯一索引约束 `(organization_id,normalized_email)` |
| `audit_logs` | id, organization_id nullable, actor_user_id nullable, action, target_type, target_id nullable, request_id, metadata | 按 organization/time、actor/time 索引；append-only 应用权限 |

所有 ID 为 UUID，`created_at/updated_at` 用数据库认可的 UTC 时间。组织创建与 OWNER membership 必须在同一事务。邀请接受与 membership 创建/复用、accepted_at 更新、审计必须在同一事务。

### 4.3 安全基线

- 密码长度 12–128；服务端用 Argon2id，参数写入哈希并有基准/升级策略；日志、审计和错误不得包含密码。
- 客户端只得到随机 session token；数据库只存 token 哈希。登录成功轮换 token；退出撤销服务端会话。
- Cookie 名稳定，设置 `HttpOnly`、生产 `Secure`、`SameSite=Lax`、`Path=/` 和明确 Max-Age。不得把 token 放 localStorage。
- 所有改变状态的 Cookie 认证请求执行 CSRF 校验（双提交 token 或等价方案），并检查允许的 Origin。
- 注册、登录、邀请创建/接受按 IP 与账号维度限流；响应和日志不得泄漏该邮箱是否已注册。可对已存在邮箱返回相同通用语义。
- 邀请 token 至少 128 bit CSPRNG 熵，只显示一次，库中存哈希，默认 72 小时过期。
- 生产错误不返回堆栈/SQL；认证比较避免明显时序差异；依赖注入的 clock/token generator 便于确定性测试。

### 4.3.1 M1 唯一实现默认值

- **会话**：128 bit 以上 CSPRNG token；服务端仅存 SHA-256/HMAC 摘要；绝对有效期 7 天，不做滑动续期；登录创建新会话，logout 撤销当前会话，logout-all 在一个事务中撤销该用户全部有效会话。
- **CSRF**：同步 token 模式。每个 session 生成独立随机 CSRF token，浏览器通过非 HttpOnly 的 CSRF Cookie 读取并放入 `X-CSRF-Token`；服务端校验允许的 Origin、header/cookie 恒时相等及 `csrf_token_hash`。会话 Cookie 仍为 HttpOnly。登出后两枚 Cookie 都清除。
- **限流**：M1 固定单 API 实例，使用进程内 token bucket，至少按 IP 和规范化邮箱双维度覆盖注册/登录，按 user 覆盖邀请；测试用注入 clock 验证恢复。M1 部署不得横向多副本；M3 若扩容再以 ADR 迁移到共享限流存储。
- **邀请唯一性**：创建邀请事务先将同组织/邮箱已过期的 PENDING 记录置为 EXPIRED，再插入；部分唯一索引保证最多一个 PENDING。接受时锁定邀请行，原子变为 ACCEPTED；撤销变为 REVOKED；并发仅一个事务成功。
- **测试数据库隔离**：每个测试 worker 使用独立 PostgreSQL database，先从空库执行完整迁移，worker 结束销毁；禁止复用开发库或依赖测试顺序。CI 容器中的 PostgreSQL 必须与基线主版本一致。
- **无响应体**：所有 `204` 响应不得携带 JSON、空对象或业务字段。

### 4.4 M1 HTTP 契约

#### Identity

| 方法与路径 | 请求要点 | 成功 | 主要失败 |
|---|---|---|---|
| `POST /auth/register` | email, password, displayName | `201` 用户摘要并设置 session/CSRF | `400/409/429` |
| `POST /auth/login` | email, password | `204` 并设置 session/CSRF | 通用 `401`，`429` |
| `POST /auth/logout` | CSRF | `204`，撤销当前会话并清 Cookie | `401/403` |
| `POST /auth/logout-all` | CSRF | `204`，撤销该用户全部会话 | `401/403` |
| `GET /me` | Cookie | `200` 用户摘要，不含 credential | `401` |

若为防枚举选择把重复注册统一为非 `409`，必须写 ADR，且 UI、契约测试一致。

#### Tenancy & Access

| 方法与路径 | 权限 | 请求/成功 |
|---|---|---|
| `POST /organizations` | 登录 | name, slug；`201` 组织摘要，actor 成为 OWNER |
| `GET /organizations` | 登录 | `200` 仅本人 ACTIVE membership 的分页列表，含本人 role |
| `GET /organizations/:organizationId` | ACTIVE 成员 | `200` 组织摘要和本人 role |
| `GET /organizations/:organizationId/members` | ACTIVE 成员 | `200` 分页成员摘要；不得返回邮箱以外敏感身份数据 |
| `POST /organizations/:organizationId/invitations` | OWNER | email, role（M1 仅 MEMBER）；`201` 邀请摘要；开发模式可含一次性 acceptUrl |
| `POST /invitations/accept` | 登录 + CSRF | token；邮箱须与登录用户规范化邮箱一致；`204` |

组织 slug 仅作展示/路由别名，授权和外键使用 organization UUID。客户端不能提交 `createdBy`、membership role、acceptedAt 等服务端字段。

### 4.5 授权判定顺序

1. 验证会话；失败 `401`。
2. 解析并校验 organization UUID。
3. 查询 actor 在该 organization 的 ACTIVE membership；不存在返回 `404`，避免泄漏组织。
4. 验证端点所需角色；成员存在但角色不足返回 `403`。
5. 加载组织内目标时同时使用 `(organization_id, target_id)` 查询；查不到返回 `404`。

不得先按 target id 全局读取再比较 organization id。前端路由保护不得替代以上步骤。

### 4.7 M1 测试矩阵

| 层级 | 必测场景 |
|---|---|
| 领域单元 | 邮箱规范化；密码策略；邀请有效/过期/已用；角色规则 |
| Repository 集成 | 唯一邮箱、membership、邀请；事务回滚；会话过期/撤销；按 organization 查询 |
| API 集成 | 每端点成功；字段缺失/额外；401/403/404/409/429；Cookie 属性；CSRF/Origin |
| 租户隔离 | A 用户不能读 B 组织/成员/邀请；双组织用户在切换后 role 正确；替换 UUID 不泄漏 |
| 并发 | 同 slug 创建只有一个成功；同邀请并发接受只成功一次且只有一个 membership |
| 安全 | 登录枚举语义；弱/超长密码；伪造/过期 session；token 不入库明文/日志；速率限制恢复 |
| 审计 | 成功动作字段完整；失败登录无密码且 actor 可空；事务失败不留下虚假成功审计 |
| 前端组件 | 表单标签/错误、提交禁用、401 跳转、403/404 呈现、组织切换 |
| 浏览器 E2E | 4.8 的完整 A/B 场景；Cookie 中无可读 bearer；退出后受保护页不可访问 |

测试数据库必须是真实 PostgreSQL；每测试隔离数据并可并行执行。不得只 mock ORM 来声称租户隔离成立。

### 4.8 决定性验收场景

从干净数据库执行，保存 API/E2E 结果与对应 request id：

1. 注册 Alice；确认数据库无明文密码/session token。
2. Alice 创建组织 A，成为唯一 OWNER；再创建组织 B，两个 role 独立。
3. 注册 Bob。Alice 在 A 邀请 Bob；Bob 接受并成为 MEMBER。
4. Bob 能读取 A 及成员列表，但创建邀请返回 `403`。
5. Bob 访问 B 的 URL 返回 `404`，响应、计数和日志均不泄漏 B 的名称或成员。
6. Alice 为 A 创建第二个给 Carol 的邀请；未登录接受为 `401`；Bob 接受因邮箱不符失败；Carol 注册后接受成功。
7. 同一邀请发起两个并发接受，只有一个业务成功，最终仅一个 membership，邀请仅一次 accepted。
8. 过期和伪造邀请均失败；响应不暴露 token 摘要或内部状态。
9. 移除 CSRF header 的创建组织、邀请、退出均被拒；错误 Origin 被拒；合法请求成功。
10. Alice logout-all 后所有旧会话立即失效；刷新/伪造 Cookie 不能恢复。
11. 审计按 request id 查到对应安全事件，且扫描日志无密码、session/invitation token。
12. 重跑迁移无变化；从 M0 数据库前向升级成功；全套门禁和浏览器流程通过。

任一跨租户泄漏、明文秘密、可重放邀请、并发重复 membership 或以 `200` 掩盖授权失败，均直接判 M1 不通过。

- 不让 AI 一次生成模块、迁移或全套测试；AI 可解释 API、提出测试反例、评审小 diff，采纳者须逐行说明。
- 不用 `any`、非空断言或关闭校验绕过类型问题；不把 ORM entity 暴露为 HTTP DTO。
- 不把用户全局标成 admin，不用前端角色作为服务端授权依据，不建立跨模块“万能 Repository”。
- 不以软删除、未来微服务、复杂 DDD 框架或事件溯源扩大 M1。

## 5. 编码任务回报模板

后续每个编码子任务完成时只回报：

1. **任务编号与行为**：例如 1.6，列出新增的用户可观察行为；
2. **文件/迁移**：实际改动范围及依赖方向；
3. **测试证据**：运行的测试层级和关键否定场景；
4. **契约变化**：端点、schema、错误码；无变化也明确写“无”；
5. **风险/遗留**：不得以隐含 TODO 交付；
6. **禁止项自查**：确认没有模板复制、跨租户全局查询或超范围架构。

M1 通过后，继续按[逐行手写里程碑](./07-手写里程碑.md)进入 M2，不得借“完善 M1”提前混入工作流、附件或 AI 代码。
