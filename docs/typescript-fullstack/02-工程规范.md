# 02｜工程与架构规范

> 本章把[技术栈基线](./01-技术栈基线.md)落成可执行规则。质量、安全和运行时门禁见[质量、安全与可观测性](./03-质量安全与可观测性.md)，全套阅读顺序见[总览](./00-手册总览.md)。

## 1. 目标与原则

本规范服务于一个 pnpm Monorepo 中的 React 前端和 NestJS 模块化单体。原则按优先级排序：

1. 正确边界优先于抽象数量；
2. 可读的显式代码优先于魔法；
3. 先完成端到端纵向切片，再横向建设平台能力；
4. 外部输入不可信，TypeScript 类型不提供运行时安全；
5. 数据库约束是最后一道一致性防线；
6. DDD 按复杂度升级，不按开发者偏好自由发挥；
7. AI 可以生成候选实现，人必须拥有需求、验证与责任。

## 2. 仓库与变更纪律

### 2.1 根目录约定

根目录统一提供以下命令语义，具体工具可演进：

| 命令 | 必须效果 |
|---|---|
| `pnpm install --frozen-lockfile` | 按 lockfile 可重复安装 |
| `pnpm lint` | 全仓 lint，warning 也导致 CI 失败 |
| `pnpm typecheck` | 不产物的严格类型检查 |
| `pnpm test` | 单元与快速组件测试 |
| `pnpm test:integration` | API、数据库、契约集成测试 |
| `pnpm test:e2e` | 关键浏览器旅程 |
| `pnpm build` | 所有受影响的可部署 app 可生产构建 |

每个内部包只暴露 `exports` 中的公开 API。禁止 app 使用相对路径越界、引用 `src/internal` 或依赖另一个 app 的源码。

### 2.2 变更单位

一个 PR 应能用一句话说明可观察结果，且同时包含所需契约、迁移、实现、测试和文档。不要提交“后端先合并、前端以后适配”的破坏性契约。大重构使用 branch-by-abstraction 或兼容层分步交付。

提交必须可审查：

- 格式化与机械改名和行为变更分开；
- 生成文件标明来源，不人工编辑；
- 新依赖解释用途、许可证、维护状态和替代方案；
- 架构边界、认证、存储、外部平台等决策写 ADR；
- 删除代码优于保留无调用的“以后会用”抽象。

## 3. 模块化单体边界

### 3.1 模块内分层

每个业务模块按职责组织，而不是全局堆放 `controllers/`、`services/`、`repositories/`：

```text
modules/<module>/
  api/              # HTTP/消息适配、请求响应映射
  application/      # 用例、授权编排、事务边界
  domain/           # 有价值时存在：规则、值对象、端口
  infrastructure/   # ORM、外部服务、队列适配
  index.ts           # 对其他模块公开的最小入口
```

简单模块可以省略空的 `domain/`，但不能把业务规则塞进 Controller 或 ORM hook。依赖方向为 `api/infrastructure → application → domain`；domain 不导入 NestJS、ORM、HTTP 或环境变量。

### 3.2 跨模块协作

- 模块只能调用对方公开的应用服务/查询端口；
- 禁止直接读取或更新其他模块的表，即使它们位于同一数据库；
- 同进程协作默认直接调用显式接口，不为“解耦”先上消息中间件；
- 同一用例需要强一致时，在一个清晰事务中协调；真正需要最终一致时才使用 outbox，不能把内存事件当可靠消息；
- 循环依赖说明边界或职责错误，不用 `forwardRef` 常态化掩盖。

### 3.3 轻量 DDD 升级规则

所有模块先从“事务脚本 + 明确应用服务 + 独立 DTO/持久化映射”开始。每个模块每季度或复杂需求进入前按下表计分：

| 信号 | 分值 |
|---|---:|
| 同一聚合存在 3 条以上必须同时保持的不变量 | 2 |
| 状态迁移多于 4 种，且受角色/时间/前置状态约束 | 2 |
| 金额、配额、时间区间等值有反复出现的运算规则 | 1 |
| 同一规则被 HTTP、任务、导入等两个以上入口复用 | 1 |
| 错误修改会造成财务、权限、合规或不可逆数据风险 | 2 |
| 与外部模型存在明显语言/生命周期冲突 | 1 |
| 只是字段 CRUD、查询和展示 | -2 |

执行规则：

- 总分 `≤2`：保持简单应用服务，不创建聚合/仓储接口；
- 总分 `3–5`：引入值对象、纯领域函数或状态机，仍可直接使用 ORM；
- 总分 `≥6`：定义聚合边界、领域服务、仓储端口和显式映射，并用不变量测试保护；
- 分数只触发设计评审，不自动生成模式代码；ADR 记录升级原因；
- 复杂度下降时允许降级并删除多余层次。

无论等级如何，命名、错误模型、事务、校验和模块公开入口保持一致。禁止同一复杂度的模块因个人偏好采用完全不同风格。

## 4. 应用层、领域层与持久化

### 4.1 Controller/API 适配层

只负责协议工作：解析、运行时校验、认证主体提取、调用一个应用用例、映射状态码与响应。不得：

- 直接调用 ORM；
- 实现资源级权限或状态规则；
- 开启事务；
- 记录含令牌/密码/完整请求体的日志；
- 向客户端返回异常堆栈。

### 4.2 应用层

应用用例负责：

1. 根据已认证主体和租户上下文加载数据；
2. 执行资源级授权；
3. 调用领域规则；
4. 定义事务边界；
5. 调用外部端口并处理幂等、重试或补偿；
6. 返回与协议无关的结果。

应用服务不能依赖浏览器 DTO 的可选字段语义。请求 DTO 必须先映射为命令/查询参数。

### 4.3 领域层

领域对象必须是普通 TypeScript，不依赖框架装饰器。使用类还是函数取决于不变量与生命周期，不因统一形式而机械套用。值对象适合金额、时间范围、规范化标识等需要构造校验与相等语义的概念。

领域错误表达可预期业务拒绝；编程错误、数据库断连等不可预期故障不能伪装成领域错误。

### 4.4 ORM 与映射

- ORM schema 是持久化模型，不是 API 或领域模型；
- 查询明确选择字段，禁止默认把敏感列带入响应映射；
- 数据库使用外键、唯一约束、非空和 check 约束保护可表达的不变量；
- 列表查询必须分页、稳定排序并有上限；
- N+1、全表扫描和无界 `IN` 在评审中阻断；
- 金额使用数据库 decimal/整数最小单位，禁止 JS 浮点直接结算；
- 时间统一存 UTC 时点；业务时区作为显式配置/字段，不把无时区字符串当时点。

## 5. 共享契约与 API

### 5.1 契约源唯一

每个端点只能有一个契约事实源，项目选择以下之一：

**方案 A：运行时 schema 为源**

- `packages/contracts` 定义与框架无关的请求、响应和错误 schema；
- TypeScript 类型由 schema 推导；
- 前后端都在边界使用 schema；
- 需要外部开放 API 时，从 schema 生成/校验 OpenAPI。

**方案 B：OpenAPI 为源**

- NestJS 产生并在 CI 固化 OpenAPI；
- 前端客户端与类型由 OpenAPI 生成；
- CI 检查生成结果无漂移；
- 服务端仍必须运行时校验输入。

禁止同时手写 interface、Nest DTO、前端类型和 OpenAPI 四份事实。共享包不包含 ORM entity、Nest provider、React hook 或服务端密钥逻辑。

### 5.2 传输格式

- ID：不透明字符串；客户端不推断序列或业务含义；
- 时间点：ISO 8601 UTC 字符串；
- 日期：`YYYY-MM-DD`，不得自动转时区；
- 金额：带币种的 decimal 字符串或约定最小单位整数；
- 枚举：契约声明的稳定字符串，新增值需考虑旧客户端；
- 可空与缺失：分别表达 `null` 和 omitted，不混用；
- 分页：外部/大表优先 opaque cursor，小型后台可用有上限的 offset；
- 写请求：关键创建/扣减操作支持幂等键。

### 5.3 兼容性

兼容变更：增加可选请求字段、增加响应字段（客户端须容忍）、新增端点。破坏性变更：删除/改名/改变语义、收紧枚举、改变可空性。破坏性变更必须先双读/双写或新增版本，迁移全部消费者后再删除旧契约。

契约 PR 必须包含：

- 正反例与边界值；
- 授权需求和错误码；
- 兼容性判断；
- 前后端契约/集成测试；
- 若涉及迁移，按 expand → migrate → contract 排序。

## 6. 统一错误模型

公开 API 返回稳定、可机器处理的错误结构：

| 字段 | 含义 |
|---|---|
| `code` | 稳定业务/平台错误码，如 `AUTH_FORBIDDEN`；客户端不得依赖文案 |
| `message` | 对用户安全的默认说明，可本地化 |
| `details` | 可选、经过白名单处理的字段错误或上下文 |
| `requestId` | 客户端报障与日志关联标识 |

规则：

- `400` 格式/校验失败，`401` 未认证，`403` 已认证但禁止，`404` 资源不可见或不存在，`409` 状态/唯一性冲突，`422` 语义无法处理，`429` 限流，`5xx` 非预期故障；
- 用判别联合或错误类表达可预期失败，`catch` 中从 `unknown` 开始收窄；
- 全局异常过滤器只做最终映射、日志和脱敏；
- 不向客户端返回 SQL、堆栈、内部 URL、密钥或第三方完整响应；
- 不能靠解析数据库错误文本决定业务逻辑；将已知约束名映射为稳定错误码；
- 前端按 `code` 决策，未知错误显示通用提示和 `requestId`。

## 7. 事务、并发与副作用

### 7.1 事务规则

- 事务围绕一个业务用例，而不是围绕仓储方法；
- 用例中的全部数据库操作显式使用同一 transaction client/context；
- 事务内禁止等待邮件、AI、对象存储等慢外部网络；
- 先提交本地状态，再由 outbox/可靠任务执行外部副作用；
- 事务尽量短，禁止在事务中等待用户输入；
- 默认接受数据库标准隔离级别；只有可复现异常与测试证据时才提高隔离级别。

### 7.2 并发控制

- 唯一性依赖数据库唯一约束，不使用“先查再插”作为唯一保护；
- 状态更新带前置状态条件或版本号，受影响行数不符返回冲突；
- 库存、余额、配额等使用原子条件更新或行锁，并做并发集成测试；
- 重试只针对明确的瞬态错误，必须有次数上限、指数退避和幂等性；
- 锁顺序固定，记录死锁并保留重试/告警；
- 接收重复 webhook、任务或写请求时使用业务幂等键与唯一约束。

## 8. 配置与密钥

配置按“启动时验证、运行时只读”管理：

1. 进程启动时读取环境变量；
2. 用 schema 校验必填、类型、范围和互斥条件；
3. 转换为类型化配置对象；
4. 业务模块通过窄接口读取，不直接散落 `process.env`；
5. 缺少关键配置立即失败，并报告变量名但不打印值。

约束：

- `.env.example` 只列变量名与非敏感示例；
- 本地 `.env` 不提交；生产密钥进入平台 secret manager；
- `NODE_ENV` 只区分运行模式，业务开关使用独立、可审计配置；
- 前端构建时变量视为公开信息；任何注入浏览器 bundle 的值都不是秘密；
- 配置变更有负责人、环境、时间和回滚记录；
- 密钥定期轮换，支持新旧凭据短期重叠，不把轮换等同于重启全部系统。

## 9. 命名与代码风格

| 对象 | 规则 | 示例形式 |
|---|---|---|
| 文件/目录 | `kebab-case` | `access-policy.ts` |
| TS 变量/函数 | `camelCase` | `resolveAccess` |
| 类型/类/React 组件 | `PascalCase` | `AccessDecision` |
| 常量 | `UPPER_SNAKE_CASE`，仅真正常量 | `MAX_PAGE_SIZE` |
| 布尔值 | `is/has/can/should` | `canEdit` |
| 用例 | 动词 + 业务对象 | `Create…`、`Approve…` |
| 数据库表/列 | `snake_case`，项目统一复数策略 | `created_at` |
| API JSON | `camelCase` | `createdAt` |
| 环境变量 | `UPPER_SNAKE_CASE` + 范围前缀 | `API_DATABASE_URL` |
| 错误码 | `UPPER_SNAKE_CASE` + 域前缀 | `AUTH_SESSION_EXPIRED` |

补充规则：

- 不使用 `IService`、`ServiceImpl` 等无信息命名；
- `Manager`、`Helper`、`Utils` 必须改为准确职责；
- interface 用能力命名，不加 `I` 前缀；
- 避免匈牙利命名和类型重复，如 `userString`；
- 导出最小化，默认不使用 barrel 汇总整个模块；
- 注释解释“为何/约束/风险”，不复述代码；公共契约说明语义与兼容性。

## 10. 前端工程规则

- 远端服务状态与本地 UI 状态分开；不要把 API 缓存复制到全局 store；
- 页面/feature 通过契约客户端访问 API，不散落裸 `fetch`；
- 表单在客户端提供即时反馈，但服务端重新验证全部输入；
- URL 承载可分享的筛选、分页和选中状态；
- 组件优先组合；抽 hook 前确认存在复用或隔离副作用的价值；
- 权限隐藏只是体验优化，服务端始终重新授权；
- 处理 loading、empty、error、partial 和 success 状态；
- 可访问性使用语义 HTML、键盘操作、焦点管理和可读错误；
- Next.js 中明确 server/client 边界，server-only 模块不得进入客户端 bundle。

## 11. AI Coding 协作规范

### 11.1 可交给 AI 的工作

- 在明确契约与测试下生成局部样板；
- 枚举边界条件、测试案例、威胁场景；
- 解释陌生 API、比较方案并提供官方来源；
- 执行机械重构、补文档、生成迁移草案；
- 对 diff 做第二视角审查。

### 11.2 不可委托的责任

人必须决定并验证：

- 需求、授权语义、数据所有权和租户隔离；
- 事务边界、迁移可逆性、删除/扣费等高风险规则；
- 依赖与许可证、外部服务数据使用条款；
- 生产密钥、真实用户数据和事故处置；
- 最终代码评审、测试证据与发布批准。

### 11.3 标准协作循环

1. **给上下文**：目标、非目标、允许修改的文件、架构约束、验收测试；
2. **先计划**：要求 AI 列假设、风险、受影响契约和最小变更；
3. **小步实现**：一次一个可评审切片，不允许无关清理；
4. **本地验证**：lint、类型、测试、迁移审查、安全检查；
5. **人工读 diff**：逐行检查权限、错误处理、事务、日志脱敏；
6. **记录来源**：外部片段、生成代码和重要设计依据可追溯；
7. **复盘**：把稳定规则沉淀为 lint、测试或本文，而非只留提示词。

提示中不得包含密钥、令牌、生产数据、客户内容或未脱敏日志。AI 输出中的包名、API、版本和引用都按“不可信外部输入”核验。禁止因“测试通过”跳过代码阅读，也禁止让 AI 关闭类型检查、删除失败测试或添加宽泛 ignore 来完成任务。

### 11.4 AI 变更评审清单

- [ ] 只修改授权范围内文件，无隐蔽的依赖或配置变更。
- [ ] 每个新 API/包/配置均在官方稳定线真实存在。
- [ ] 未把 DTO、ORM 实体、秘密或服务端模块泄漏给前端。
- [ ] 失败、并发、权限和回滚路径均有测试或说明。
- [ ] 无大面积 `any`、忽略规则、静默 fallback 或占位生产数据。
- [ ] 生成代码许可证与来源可接受。
- [ ] 人类评审者能解释关键代码，而非仅相信模型结论。

## 12. 架构验收清单

- [ ] 模块按业务能力组织，Controller 不含规则或 ORM 调用。
- [ ] 简单模块与核心域均按 DDD 计分规则选择复杂度。
- [ ] 契约事实源唯一，所有外部输入有运行时校验。
- [ ] 错误码稳定，客户端不依赖错误文案。
- [ ] 事务短且围绕用例，外部副作用不在数据库事务内等待。
- [ ] 配置启动时验证，浏览器 bundle 中无秘密。
- [ ] 数据表约束、并发策略和幂等边界已定义。
- [ ] AI 生成变更由人逐行审查并通过统一门禁。
