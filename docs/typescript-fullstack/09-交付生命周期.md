# 09｜交付生命周期：从需求到可发布制品

> 本章是[手册首页](./00-手册总览.md)中的交付流程章节。部署、迁移和运行时处置见[第 10 章](./10-部署与运维.md)，可打印执行的检查项见[第 11 章](./11-执行清单与速查.md)。

## 1. 目标与起步约束

目标是围绕 TypeScript 全栈项目建立短反馈环：

`可验收需求 → 小型 ADR → 纵向切片 → 自动化验证 → 不可变制品 → 分环境晋级`

起步采用**模块化单体 + 一个关系数据库 + 必要的后台任务**。不要为了“生产级”预先引入微服务、Kubernetes 或事件溯源。只有当团队已经测得独立伸缩、故障隔离或独立发布的硬需求时，才另写 ADR 评估升级。

TypeScript 项目需要特别注意：

- `package.json` 脚本是统一的任务入口，真正约束应落在锁文件、CI 和工具配置中。
- TypeScript 类型在运行时通常不存在；接口类型不能代替输入校验、数据库约束或授权检查。
- NestJS 的 provider/module 用于依赖与模块组织，但不要把每个实体机械拆成 Repository/Service/Controller。
- Pull Request（PR）是变更审计单元；ADR 是架构取舍记录，不是长篇设计审批。

## 2. 需求卡模板

每个可交付切片只解决一个可观察问题。复制以下结构到 issue，而不是先写“完成前后端开发”：

```text
标题：[能力] 对 [角色] 产生的结果

背景/问题：
目标用户与使用场景：
业务结果（可衡量）：
范围内：
范围外：

验收示例（Given / When / Then）：
1. Given ... When ... Then ...
2. Given 无权限/非法输入/重复请求 ... Then ...

数据与租户边界：
- 读取/写入哪些数据？
- 租户隔离、保留期、敏感级别是什么？

接口与兼容性：
- 新增或改变的 HTTP/事件/页面契约：
- 是否向后兼容；弃用计划：

非功能预算：
- 延迟/吞吐/可用性目标：
- 日志、指标、审计要求：
- 安全和隐私要求：

发布与验证：
- 功能开关或灰度方式：
- 数据迁移：
- 监控信号：
- 回滚条件与责任人：

不确定项/依赖：
```

### 切片准入（Definition of Ready）

- 用户、结果、边界和至少一个失败场景明确。
- 验收条件可由测试或观察证明，不使用“正常”“友好”“高性能”等模糊词。
- 契约、数据迁移、权限和可观测性影响已识别。
- 工作能在一个小 PR 或少量连续 PR 中完成；否则继续纵向拆分。
- 高风险或难以逆转的技术选择已经有 ADR。

## 3. ADR：记录决定，不记录会议

将 ADR 作为仓库内版本化文本，编号保持稳定，例如 `ADR-0007`。状态至少包括：`提议`、`接受`、`被取代`、`拒绝`。

```text
# ADR-NNNN：一句话决定
日期：
状态：
决策人：

## 背景与约束
哪些事实迫使我们决定？哪些是不确定假设？

## 决策驱动因素
例如：团队能力、恢复目标、成本、合规、可逆性。

## 候选方案
A / B / 保持现状；列出真实优缺点与运行成本。

## 决定
选择什么，适用边界是什么。

## 后果
获得什么、承担什么、如何验证。

## 退出/复审条件
哪些指标或日期触发重评？由什么方案取代？
```

以下情况通常需要 ADR：认证方式、数据库/ORM、租户隔离策略、公共契约兼容规则、部署拓扑、恢复目标、引入新的运行时基础设施。命名、单个函数实现或易于回退的小依赖无需 ADR。

## 4. 分支、提交与 PR

### 4.1 推荐流程

采用短生命周期主干开发：

1. `main` 始终可发布并受保护，禁止直接推送。
2. 从最新 `main` 建立短分支，如 `feat/issue-123-invite-member`、`fix/issue-456-timeout`。
3. 高频同步主干；分支以小时或少数几天计，而不是以迭代计。
4. 未完成能力通过服务端判定的功能开关隔离；不要长期保留“大合并分支”。
5. 合并前必须通过必需检查和至少一名非作者评审；高风险迁移、安全边界需要领域责任人评审。
6. 合并后由 CI 从同一提交生成一次制品，再晋级到不同环境；禁止每个环境重新构建。

团队规模很小时，仍应保留 PR 与自动检查；可以降低审批人数，但不能用口头确认代替可追溯记录。

### 4.2 提交约定

使用一致、可检索的前缀即可，例如：

```text
feat(auth): add session revocation endpoint
fix(tenant): scope document query by tenant id
refactor(api): extract validation without behavior change
test(workflow): cover duplicate transition
chore(deps): update validated minor versions
```

每个提交应：

- 只表达一个意图，能独立审阅；不要把格式化全仓与行为修改混在一起。
- 说明“为何”，必要时引用 issue/ADR；不要复述 diff。
- 不包含密钥、生产数据、生成物或无关锁文件变化。
- 在数据库契约变化时同时包含迁移、兼容代码和测试。

是否使用 squash 由团队统一决定。关键是 PR 页面保留需求、风险、验证和发布信息，而非追求提交历史形式。

### 4.3 PR 模板

```text
## 关联
Issue：
ADR（如有）：

## 变更与不变项
- 做了什么：
- 明确没做什么：

## 风险
- 权限/租户/敏感数据：
- 契约兼容：
- 数据迁移与锁表风险：
- 性能与依赖：

## 验证证据
- 自动化测试：
- 人工验证（步骤与结果，不上传真实敏感数据）：

## 发布
- 配置/开关：
- 观测指标与预期：
- 回滚条件和方法：
```

### 4.4 评审顺序

评审者按顺序检查：

1. **需求正确性**：验收条件与范围是否匹配。
2. **安全边界**：认证、授权、租户过滤、输入校验是否在服务端执行。
3. **契约与数据**：兼容性、事务边界、唯一性/外键、迁移是否可部署。
4. **失败行为**：超时、重试、幂等、并发、错误映射是否明确。
5. **可运行性**：结构化日志、指标、健康检查和回滚信号是否具备。
6. **可维护性**：命名和依赖方向是否清晰，测试是否验证行为而非实现细节。

避免只评格式，也避免以个人偏好阻塞。格式交给工具；架构异议引用既有规则，规则缺失且影响长期决策时补 ADR。

## 5. CI：把仓库变成可验证制品

### 5.1 PR 必需检查

推荐按“快速失败”排序：

1. 锁文件一致性、依赖安装及受支持 Node.js/package manager 版本。
2. 密钥扫描、依赖漏洞与许可证策略检查。
3. 格式、lint、TypeScript 类型检查。
4. 单元测试。
5. 使用临时 PostgreSQL 的迁移验证和集成测试。
6. API 契约兼容检查。
7. 构建前端、后端和共享包。
8. 关键用户路径的少量端到端测试。
9. 容器镜像构建与镜像扫描。

这些命令只能作为**结构示意**，必须替换为本仓库实际脚本，不能直接当成通用成品：

```sh
# 示意：CI 中使用锁文件严格安装
<package-manager> install --frozen-lockfile
<package-manager> run lint
<package-manager> run typecheck
<package-manager> run test
<package-manager> run build
```

CI 需固定运行时主版本与包管理器版本；缓存键至少包含锁文件摘要和运行时版本。缓存失败只能变慢，不能改变产物。测试报告、覆盖率、SBOM、镜像摘要和迁移检查结果应作为构建证据保存。

### 5.2 覆盖率与门禁

不要用全局覆盖率数字掩盖薄弱核心域。最低要求是：

- 权限、租户隔离、状态转换、计费/用量等高风险规则必须有行为测试。
- 修复缺陷必须先能被测试复现，或说明为何只能通过运行时监控验证。
- 新代码不得降低团队设定的基线；豁免要有期限和责任人。
- 不稳定测试不得简单重跑至通过，应隔离、登记并限期修复。

### 5.3 主干构建与制品晋级

合并到 `main` 后：

1. 重跑必需检查。
2. 生成带提交 SHA 与语义版本/构建号的不可变镜像。
3. 生成或附加 SBOM、来源证明、数据库迁移清单。
4. 以镜像 digest 而非可变 `latest` 标识候选制品。
5. 自动部署测试/预发布环境并执行 smoke test。
6. 生产环境采用人工批准或策略批准，**晋级同一 digest**。

环境差异只能来自受控配置与密钥，不应来自不同源码分支或重新构建。

## 6. CD 与环境契约

至少定义：

| 环境 | 用途 | 数据 | 发布触发 | 保留 |
|---|---|---|---|---|
| 本地 | 单人开发和快速测试 | 合成/匿名化 | 开发者 | 可重建 |
| CI 临时环境 | 自动测试 | 测试夹具 | PR/流水线 | 短期销毁 |
| 预发布 | 迁移、集成、发布演练 | 合成或严格脱敏 | 主干候选 | 接近生产配置 |
| 生产 | 真实业务 | 受控生产数据 | 审批后晋级 | 按保留策略 |

每个环境都应明确：

- 配置 schema、必填项和启动时校验；缺失配置应失败并给出明确错误。
- 密钥由平台密钥服务或受控 secret 文件注入，不进入 Git、镜像或前端 bundle。
- 外部依赖的 endpoint、超时、重试和限流。
- 数据库迁移身份与应用运行身份分离；应用通常不应持有 DDL 权限。
- `/live` 只回答进程是否存活，`/ready` 验证能否接流量；避免把所有第三方依赖都绑到存活探针上造成级联重启。

## 7. 发布计划与交接

每次生产发布至少留下：

```text
版本/镜像 digest：
包含的 issue 与 ADR：
负责人、批准人、发布时间窗：
配置和迁移变化：
迁移前备份/恢复点：
功能开关默认值：
观察面板和告警：
成功标准：
中止阈值：
应用回滚步骤：
数据前滚/恢复步骤：
业务通知：
```

数据库回滚不能只写“回退镜像”。应使用 expand/contract：

1. **Expand**：先增加向后兼容的列、表或索引。
2. 部署可同时读写新旧结构的应用，必要时后台回填。
3. 观察并切换读取路径。
4. **Contract**：经过至少一个安全发布窗口后再删除旧结构。

具体迁移、备份、回滚和事故流程见[第 10 章](./10-部署与运维.md)。

## 8. 完成定义（Definition of Done）

一个切片只有在以下条件成立时才“完成”：

- 验收条件通过，范围外项目没有被暗中加入。
- 类型检查、静态检查、测试、构建和安全门禁通过。
- 契约与迁移兼容策略已验证。
- 服务端授权、租户隔离和审计要求有测试证据。
- 日志、指标、追踪上下文足以定位主要失败。
- 操作说明、配置 schema、ADR 和用户文档按需更新。
- 候选制品可追溯到提交，预发布 smoke test 通过。
- 发布、观察和回滚责任明确。
