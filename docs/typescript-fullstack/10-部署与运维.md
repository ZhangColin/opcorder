# 10｜部署与运维：从容器到恢复演练

> 返回[手册首页](./00-手册总览.md)。本章承接[第 09 章交付生命周期](./09-交付生命周期.md)，相关验收项汇总在[第 11 章生产就绪清单](./11-执行清单与速查.md#5-生产就绪清单)。

## 1. 运行模型与选择

起步系统采用模块化单体：

- 一个 Web 前端（静态资源或 Node.js 服务，取决于 React/Vite 或 Next.js 渲染模式）。
- 一个 NestJS API/后台任务进程；并发任务增多时可使用同一代码库的独立 worker 进程。
- 一个 PostgreSQL。
- 一个 TLS 终止层或托管平台入口。
- 文件存储、邮件、AI 等使用有明确超时和配额的外部服务。

两条受支持路径：

| 路径 | 适合 | 团队承担 | 主要风险 |
|---|---|---|---|
| 单机 Docker Compose | 小流量、预算敏感、能承担 Linux 值守 | OS、TLS、数据库、备份、监控、容量、恢复全部责任 | 单机故障域、人工运维 |
| 托管部署 | 希望减少值守，接受平台约束 | 应用、迁移、配置、SLO；平台承担部分主机/数据库工作 | 厂商限制、费用、误以为“托管即免运维” |

不要以“以后可能需要”为由起步上微服务、Kubernetes 或事件溯源。单机需要高可用时，优先评估托管数据库和可快速重建的应用主机，而不是直接搭建集群。

## 2. 容器镜像基线

### 2.1 构建要求

- 多阶段构建，builder 与 runtime 分离；runtime 只含生产依赖和编译产物。
- 固定基础镜像到明确版本，关键环境可固定 digest；建立定期更新流程。
- 以非 root 用户运行，根文件系统尽可能只读，临时文件写到受控目录。
- 不在镜像层、构建参数或前端环境变量中嵌入密钥。
- `.dockerignore` 排除 `.git`、本地环境文件、测试产物和无关源码。
- 记录 OCI labels：提交 SHA、源码地址、构建时间、版本。
- CI 生成 SBOM 并扫描 OS 与 npm 依赖；严重漏洞按策略阻断或限时豁免。
- 捕获 `SIGTERM`，停止接收新请求，等待有界时间后退出；任务消费者要安全归还未完成任务。

下面仅是验证思路，镜像名、端口、路径和探针必须按项目调整：

```sh
# 示意，不是可直接运行的通用命令
docker build --tag <registry>/<application>:<commit-sha> <build-context>
docker run --rm --read-only --user <non-root-uid> \
  --env-file <non-production-env-file> \
  --publish <host-port>:<container-port> \
  <registry>/<application>:<commit-sha>
```

不要只验证“容器能启动”；还需验证健康探针、只读文件系统、优雅关闭、时区/编码、内存限制下行为和日志输出到 stdout/stderr。

### 2.2 配置和密钥

应用启动时用运行时 schema 校验环境变量，错误应指出缺失键但不打印值。配置分三类：

1. 非敏感、随版本变化：仓库中的默认配置。
2. 非敏感、随环境变化：部署平台配置。
3. 密钥：secret manager 或权限受限的挂载文件。

密钥必须有所有者、用途、创建时间、轮换周期和撤销流程。轮换采用“新旧短期并存 → 切换 → 验证 → 撤销旧值”，并做演练。

## 3. HTTPS 与网络边界

- 公网只开放 `80/443`；HTTP 永久重定向到 HTTPS。
- TLS 1.2 及以上，证书自动申请、续期并监控到期时间。
- 数据库、管理端口、指标端点不直接暴露公网；用主机防火墙和平台网络规则双重限制。
- 反向代理设置请求体上限、头部上限、读取/连接超时与基础限流。
- 只有经过配置的可信代理才可提供 `X-Forwarded-*`；否则攻击者可能伪造协议或客户端地址。
- 浏览器响应设置 HSTS（确认全站 HTTPS 后逐步提高期限）、CSP、`X-Content-Type-Options` 和合适的 Referrer Policy。
- Cookie 使用 `Secure`、`HttpOnly`、合适的 `SameSite` 与最小作用域。

证书续期告警必须早于到期至少数周，且要模拟一次续期失败。DNS、域名注册账户和证书账户开启 MFA，并记录紧急接管方式。

## 4. 单机 Docker Compose 路径

### 4.1 拓扑

一台受支持的 Linux 主机运行：

- `reverse-proxy`：TLS 终止与路由。
- `web` / `api` / 可选 `worker`：使用固定镜像 digest。
- `postgres`：仅内部网络，数据挂载到专用持久卷。
- 轻量监控/日志采集组件（容量不足时也必须至少有外部可用性探测）。

Compose 文件应定义健康检查、重启策略、CPU/内存约束、日志轮换、内部网络和持久卷。不要把数据库密码写入 Compose 文件；不要把 PostgreSQL 端口发布到公网。

### 4.2 首次上线步骤

1. 创建专用部署用户，禁用密码 SSH 和 root 远程登录，配置 MFA/受控密钥。
2. 更新 OS，启用安全补丁、主机防火墙、时间同步和磁盘空间告警。
3. 安装受支持版本的 Docker/Compose 插件并记录升级策略。
4. 创建目录、卷、secret 文件及最小权限；确认备份目标位于不同故障域。
5. 配置 DNS、反向代理和证书，先以非生产域名验证。
6. 拉取按 digest 固定的镜像，核对签名/来源证明（若已启用）。
7. 备份数据库，单独运行迁移任务；成功后启动应用。
8. 运行 smoke test：主页、认证、授权失败路径、读写、健康探针。
9. 启用外部监控和告警，观察资源与错误率，再开放流量。
10. 保存版本、迁移、负责人、时间和验证证据。

以下只是 Compose 操作顺序示意，服务名和参数必须与实际文件核对：

```sh
# 示意：先解析配置并检查最终结果
docker compose -f <compose-file> config
# 示意：拉取固定制品、执行一次性迁移、再更新服务
docker compose -f <compose-file> pull
docker compose -f <compose-file> run --rm <migration-service>
docker compose -f <compose-file> up -d --remove-orphans
```

### 4.3 单机特有控制

- 保持基础设施与 Compose 配置可在空主机重建；每季度至少在另一台临时主机演练。
- 数据库卷快照不能替代 PostgreSQL 一致性备份。
- 监控系统不能只在同一台主机上，否则主机宕机时无法告警。
- 预留磁盘和 inode；设置容器日志轮换，数据库 WAL 和备份保留上限。
- 明确单机 RTO，准备 DNS 切换、替代主机和恢复凭据。

## 5. 托管部署路径

选择支持不可变镜像、HTTPS、自定义域名、secret、健康检查、滚动/蓝绿更新和日志导出的平台；数据库优先选择带时间点恢复（PITR）的托管 PostgreSQL。

上线步骤：

1. 用 IaC 或可审计配置声明应用、网络、数据库、域名、环境变量和权限。
2. 将 CI 身份限制到指定项目/环境，使用短期身份联合而不是长期云密钥。
3. 创建预发布和生产环境，隔离数据库、secret 和外部服务配额。
4. 配置数据库连接池；总连接上限须考虑实例数、worker 与管理预留。
5. 将固定 digest 部署预发布，执行迁移、smoke test 和兼容验证。
6. 批准后晋级同一 digest；按平台能力灰度或蓝绿切流。
7. 导出日志、指标和审计记录到独立保留位置。
8. 验证平台备份只是“存在”还不够：实际恢复到隔离实例并校验。

需要逐项确认的厂商问题：

- 实例是否休眠、临时磁盘是否会丢失、请求/任务最长执行时间是多少？
- 滚动发布期间新旧版本会并存多久？健康检查失败如何处理？
- 出站 IP、私网连接、数据库连接限制和区域故障能力是什么？
- 日志、备份、PITR 的保留期和导出方式是什么？
- 如何导出镜像、数据、DNS 和密钥以降低退出成本？

## 6. 数据库迁移

### 6.1 规则

- 迁移文件进入版本控制，已经在共享环境执行的迁移禁止修改，只能追加。
- 生产迁移使用专用身份；应用身份无 DDL 权限。
- CI 从空库执行全部迁移，并从上一个发布版本数据库演练升级。
- 上线前评估表大小、锁类型、预计时长、磁盘增长和复制/PITR 影响。
- 大表回填拆成可暂停、可重入、有限批次的后台作业，记录进度。
- 禁止在高峰期直接添加高代价约束、改写整表或删除仍被旧版本使用的列。

### 6.2 Expand/contract 发布

1. 新增可空列/新表/并发索引等兼容结构。
2. 发布兼容新旧 schema 的应用。
3. 限速回填并校验行数、校验和或业务不变量。
4. 切换读取，观察错误、延迟和旧路径使用量。
5. 添加约束或收紧非空。
6. 至少跨过约定的回滚窗口后再删除旧结构。

每个迁移都回答：

```text
影响对象和预计行数：
所需锁及最长可接受时间：
磁盘/WAL 增量：
应用版本兼容区间：
超时/中止方法：
验证查询或业务不变量：
失败后：继续前滚 / 恢复备份 / 人工修复
```

ORM 的“自动同步 schema”只能用于可丢弃的本地环境，生产必须运行显式迁移。

## 7. 备份与恢复

### 7.1 先定义目标

- **RPO**：最多允许丢失多久的数据。
- **RTO**：从事故开始到关键能力恢复最多多久。

业务负责人批准目标，运维方案据此选择全量备份、增量/WAL 归档和 PITR。示例：声称 RPO 15 分钟，就必须证明 WAL 持续归档且告警及时；每日备份无法满足该目标。

### 7.2 最低策略

- PostgreSQL 定期基础备份 + 满足 RPO 的 WAL/PITR；备份加密并位于独立账户或故障域。
- 对象存储保存附件版本或启用适合的保留策略；数据库备份不包含外部对象本体。
- 备份配置、基础设施声明、必要审计数据和恢复运行手册。
- 执行 3-2-1 思路：至少三份副本、两种介质/故障域、一份异地或隔离。
- 对备份成功、大小突变、归档延迟、保留删除和恢复测试结果告警。
- 定期验证删除策略及法律保留，避免“永久备份”违背隐私要求。

### 7.3 恢复演练

至少每季度：

1. 声明目标时间点和事故假设。
2. 在隔离网络创建空环境，禁止误连生产外部服务。
3. 恢复数据库与对象；应用使用与该 schema 兼容的镜像。
4. 校验数据库可启动、迁移版本、关键表行数、抽样业务不变量和附件引用。
5. 执行关键用户路径，但阻止真实邮件/支付/AI 调用。
6. 记录实测 RPO/RTO、失败步骤、手工依赖与改进负责人。
7. 销毁恢复环境并按策略清理敏感副本。

只看备份任务“绿色”不算验证；**可恢复性只能由恢复证明**。

## 8. 可观测性与告警

### 8.1 信号

- **日志**：JSON 结构化输出，包含时间、级别、服务、版本、环境、request/trace ID、租户的不可逆标识；禁止 token、密码、完整请求体和敏感个人数据。
- **指标**：请求率、错误率、延迟分位数、饱和度；数据库连接/慢查询；任务积压/失败；外部服务超时；关键业务成功率。
- **追踪**：HTTP → 应用 → 数据库/队列/外部 API 传播 trace context；采样策略兼顾成本与错误保留。
- **审计**：谁在何时对什么资源做了什么、结果如何；审计日志与调试日志分开保留和授权。

### 8.2 SLI/SLO 示例结构

```text
用户旅程：已登录用户读取工作项
SLI：满足状态码与延迟阈值的有效请求 / 全部有效请求
SLO：滚动 28 天达到团队批准的目标
排除：明确列出的计划维护或客户端取消（需防止滥用）
告警：短窗口快速燃烧 + 长窗口慢速燃烧
```

具体百分比必须来自业务承诺和现状测量，不应抄写示例。每个可行动告警包含：影响、严重级别、面板、runbook、责任组和升级路径。

### 8.3 最小告警集

- 外部可用性失败、错误率和延迟异常。
- 数据库空间、连接池饱和、复制/WAL 归档失败、备份失败。
- CPU、内存、磁盘、inode 与容器反复重启。
- 后台任务积压、永久失败和最老任务年龄。
- TLS 证书将到期、域名或关键 secret 轮换逾期。
- 安全异常：大量认证失败、权限拒绝激增、审计链路中断。

低紧急度事件进入工单，不应半夜呼叫。每月复盘误报、漏报和无人处理告警。

## 9. 发布、验证与回滚

### 9.1 发布前

- 发布记录完整，值守者在线，变更窗口和冻结规则清楚。
- 镜像 digest、SBOM、扫描和签名/来源证据可查。
- 迁移在生产规模近似数据上计时，备份或恢复点已验证。
- 仪表盘已打开，当前基线已截图/记录。
- 应用回滚版本、配置回滚值和功能开关已确认。

### 9.2 发布中与发布后

1. 必要时先执行兼容迁移。
2. 部署小比例实例/绿色环境，运行自动 smoke test。
3. 观察错误率、P95/P99、资源、数据库锁、业务成功率。
4. 分步放量；每步有等待窗口和中止阈值。
5. 完成后记录结果，继续观察一个约定窗口。

### 9.3 回滚决策

| 变化 | 首选处置 |
|---|---|
| 纯应用、schema 兼容 | 回滚到上一镜像 digest |
| 可关闭的新功能 | 关闭功能开关，再评估镜像回滚 |
| 配置错误 | 恢复上一已知配置并重启/重载 |
| 已执行兼容的 expand 迁移 | 保留新增结构，回滚应用 |
| 破坏性迁移或数据错误 | 停写；按预案前滚修复或时间点恢复 |
| 外部依赖故障 | 降级/熔断/暂停任务，避免重试风暴 |

不要在事故中临时编写“向下迁移”删除数据。数据恢复会覆盖事故点后的合法写入，必须由事故负责人和业务负责人明确决策，并规划数据对账/重放。

## 10. 事故响应

严重级别示例：

- **SEV-1**：核心能力大面积不可用、数据泄露/损坏或安全入侵。
- **SEV-2**：重要能力显著降级、有替代路径或影响有限租户。
- **SEV-3**：局部缺陷，无即时重大影响，按工单处理。

### 10.1 角色

- 事故指挥官：定级、分工、决策节奏，不亲自陷入所有排查。
- 技术处置：诊断和缓解。
- 沟通负责人：内部时间线、客户/状态页更新。
- 记录员：时间、证据、命令、决定和结果。

小团队可一人兼任，但角色职责仍需明确。

### 10.2 处置节奏

1. **确认与定级**：承认告警，建立事故频道/工单，指定指挥官。
2. **保护**：优先阻止数据继续损坏或泄露，必要时停写、撤销凭据。
3. **缓解**：回滚、关闭开关、扩容、隔离依赖；先恢复服务再追根因。
4. **沟通**：按承诺频率更新“影响、正在做什么、下次更新时间”，不猜测恢复时间。
5. **恢复与验证**：用用户旅程和数据不变量证明恢复，继续观察。
6. **复盘**：保留无责时间线，区分触发原因、促成条件和检测缺口。

复盘必须形成带负责人和期限的改进项，并验证完成；“提醒大家小心”不是有效行动。

## 11. 故障演练计划

先桌面推演，再在预发布注入故障，最后才考虑受控生产演练。禁止无观察、无停止条件的“随机破坏”。

| 场景 | 注入/模拟 | 预期控制 | 验证 |
|---|---|---|---|
| 应用进程退出 | 终止一个实例 | 重启且无未界定写入 | 探针、告警、恢复时间 |
| PostgreSQL 暂不可达 | 阻断预发布连接 | 有界超时，无重试风暴 | 连接池、错误率、恢复 |
| 外部 AI/邮件超时 | 测试替身延迟/失败 | 降级、任务可重试且幂等 | 用户提示、队列年龄 |
| 磁盘接近满 | 限制测试卷容量 | 提前告警，运行手册有效 | 阈值和清理步骤 |
| 证书续期失败 | 桌面推演/测试域名 | 到期前告警，可人工替换 | 责任人与凭据 |
| 错误应用发布 | 部署已知失败候选 | 自动中止并回滚 digest | 实测恢复时间 |
| 误删数据 | 隔离环境删除夹具 | PITR/备份恢复并校验 | 实测 RPO/RTO |
| secret 泄露 | 桌面推演 | 撤销、轮换、审计影响 | 完成时间和遗漏点 |

每次演练记录假设、范围、批准人、停止条件、观测信号、结果和改进项。检查表见[第 11 章](./11-执行清单与速查.md)。
