# 03｜质量、安全与可观测性基线

> 本章定义“可以合并、可以发布、可以运营”的最低标准。技术选择见[技术栈基线](./01-技术栈基线.md)，模块、契约、事务与 AI 协作见[工程规范](./02-工程规范.md)，导航见[总览](./00-手册总览.md)。

## 1. Definition of Done

任一生产变更只有同时满足以下条件才算完成：

- 需求验收条件和非目标明确；
- lint、格式、严格类型检查、构建全部通过；
- 按风险层级补齐单元、集成、契约或端到端测试；
- 数据库变更有迁移、兼容部署顺序和恢复方案；
- 完成认证、授权、输入、敏感数据与依赖风险检查；
- 关键路径具有结构化日志、指标和 trace 关联；
- 操作手册、告警或仪表盘随行为变化同步更新；
- 至少一名非作者审查；高风险变更实行双人批准；
- 没有用 ignore、跳过测试或静默 fallback 掩盖失败。

## 2. 持续集成门禁

### 2.1 PR 必过流水线

按“尽快失败”排序：

1. lockfile 一致性、禁止秘密与许可证/依赖策略检查；
2. 格式检查、lint（零 warning）、TypeScript 严格检查；
3. 单元与组件测试；
4. 生产构建和包边界检查；
5. 使用临时 PostgreSQL 的迁移与集成测试；
6. OpenAPI/schema 漂移与兼容性检查；
7. 受影响的 Playwright 冒烟旅程；
8. 容器镜像漏洞扫描与软件物料清单（SBOM）。

主分支保护要求：禁止直接推送；必需检查不可绕过；评审意见解决后才能合并；合并后的产物以不可变 commit SHA 标识，不在不同环境重复构建。

### 2.2 风险分级

| 等级 | 示例 | 最低额外证据 |
|---|---|---|
| 低 | 文案、无行为文档、样式 | lint/构建、截图或组件验证 |
| 中 | 普通查询、非敏感表单、兼容 API | 单元 + 集成/组件测试 |
| 高 | 认证授权、租户边界、迁移、并发、金额、删除 | 双人审查、失败路径与并发测试、预发布验证、回滚步骤 |
| 紧急 | 已利用漏洞、生产阻断 | 缩短但不取消审查；事后补测试与复盘 |

覆盖率只作趋势和漏测提示，不以单一百分比代替风险判断。新增/修改的关键领域规则要求分支与反例覆盖；仓库可设置合理下限防止覆盖率倒退。

## 3. 测试策略

### 3.1 测试分层

| 层次 | 测什么 | 不测什么 |
|---|---|---|
| 单元 | 纯领域规则、映射、校验、状态机 | 框架装饰器、第三方库内部实现 |
| 组件 | 用户可见交互、可访问性、表单状态 | 私有 state、DOM 结构快照细节 |
| 集成 | Controller 到数据库、约束、事务、授权、外部适配器 | 用 mock 数据库声称验证 SQL |
| 契约 | schema/OpenAPI 兼容、请求响应正反例、消费者假设 | 与集成测试完全重复 |
| E2E | 少量关键用户旅程和部署连通性 | 穷举所有边界组合 |
| 非功能 | 并发、性能、安全、恢复 | 每个 PR 都跑完整压测 |

建议测试组合：大量快速单元/组件测试，中量真实数据库集成测试，少量稳定 E2E。NestJS 模块、ORM 和 PostgreSQL 行为必须用真实 PostgreSQL 验证，不能以 SQLite 或内存 mock 替代。

### 3.2 测试可重复性

- 测试独立，可并行，无执行顺序依赖；
- 固定时钟、随机种子和外部响应；禁止任意 sleep；
- 数据工厂只给合理默认值，测试明确覆盖与断言相关字段；
- 每个测试拥有隔离数据库/schema/事务策略，并可靠清理；
- 外部 API 在单元/常规集成测试中使用协议级 fake；预发布再做受控沙箱验证；
- 失败必须保留可诊断的 request ID、trace、截图/视频（E2E）；
- flaky 测试视为缺陷：隔离需有负责人和到期日，不能无限重试变绿。

### 3.3 必测场景

每个写用例至少覆盖：

- 成功；
- 输入边界与未知字段策略；
- 未认证、错误角色、跨租户/非所有者访问；
- 资源不存在与不可见；
- 重复提交、并发更新、唯一性冲突；
- 数据库或外部依赖失败；
- 日志与错误响应不泄露敏感信息。

金额、配额、状态流转和删除操作还需属性/表驱动测试与真实并发测试。权限测试以“默认拒绝”为起点，不只测允许路径。

## 4. 数据库迁移规范

### 4.1 基本规则

- schema 只由版本化迁移改变；生产禁用 ORM 自动同步；
- 已进入共享环境的迁移不可修改或重排，只能追加修正；
- 迁移文件与使用它的代码同 PR，生成 SQL 必须人工阅读；
- CI 从空库执行全部迁移，并从上一发布版本做升级演练；
- 生产迁移使用权限受限的专用身份，记录版本、耗时与结果；
- 大表变更先评估锁、扫描、磁盘和复制延迟。

### 4.2 Expand → Migrate → Contract

破坏性变更至少跨两个发布：

1. **Expand**：添加可空列/新表/兼容索引；旧代码仍能运行；
2. **Migrate**：部署双读/双写或兼容代码，分批回填，校验计数与校验和；
3. **Contract**：确认所有实例和任务不再使用旧结构，再加非空/删除旧列；
4. **Cleanup**：移除临时代码、指标与开关。

不要依赖“回滚应用就会回滚数据”。删除、类型收窄、重命名和大规模回填必须有备份/恢复或前向修复方案。回填任务需可暂停、可重入、限速并输出进度。

### 4.3 发布前迁移检查

- [ ] SQL 无意外删表/删列、全表锁或无界更新。
- [ ] 新旧两个应用版本均可在 expand 后 schema 上运行。
- [ ] 新索引采用数据库支持的低锁策略并考虑事务限制。
- [ ] 数据回填与 schema DDL 分开，可观察且可重试。
- [ ] 预计时长、磁盘增长、锁等待阈值和终止条件明确。
- [ ] 最近备份已验证可恢复，而非仅显示“备份成功”。

## 5. 身份认证与授权

### 5.1 认证

优先采用成熟 OIDC/OAuth 2.1 身份提供商或经过审查的服务端会话方案，不自行设计密码学协议。

- 浏览器首选 Secure、HttpOnly、SameSite 合理配置的 cookie；
- cookie 会话的写操作必须防 CSRF；
- token 校验 issuer、audience、签名算法、有效期和时钟偏差；
- refresh token 轮换并检测重放；
- 登录、找回、MFA 和敏感操作限流；
- 会话撤销、设备退出和凭据轮换路径必须可用；
- 密码若本地保存，采用当前推荐的自适应哈希参数与独立 salt，不记录明文。

不得把长期令牌放入 `localStorage` 作为默认方案，不得将身份提供商返回的任意声明直接当内部授权事实。

### 5.2 授权与多租户

每次请求执行：

1. 认证主体；
2. 解析可信租户上下文（不能仅信任客户端传入 ID）；
3. 在查询本身或仓储边界施加租户过滤；
4. 应用层检查角色/能力；
5. 对已加载资源做所有权、状态和关系授权；
6. 对敏感成功/拒绝写审计事件。

规则：

- 默认拒绝，允许项显式列出；
- UI 隐藏按钮不是授权；
- 管理员也必须受租户范围和审计约束；
- 跨租户 ID 返回时避免泄露资源存在性；
- 后台任务、导出、搜索索引和缓存使用相同租户边界；
- 如果采用 PostgreSQL RLS，它是纵深防御，不能替代应用授权；连接池上下文必须测试。

## 6. 输入、输出与常见 Web 风险

### 6.1 输入校验

所有 HTTP、WebSocket、队列、文件、webhook、环境变量和第三方 API 响应都在入口运行时校验：

- 字段类型、长度、格式、数值范围、枚举和嵌套深度；
- 默认拒绝或剥离未知字段，策略全项目一致；
- 上传限制 MIME、扩展名、大小和数量，并检查实际内容；
- webhook 先用原始 body 验签，再解析和幂等处理；
- URL 抓取采用 allowlist/解析后 IP 检查，阻止内网、元数据地址和重定向绕过；
- 正则避免灾难性回溯；JSON/压缩包限制体积和展开比。

### 6.2 注入与输出

- SQL 只使用 ORM 参数绑定或参数化查询；
- shell 命令优先结构化 API，禁止拼接不可信字符串；
- React 默认转义文本，不使用不可信 `dangerouslySetInnerHTML`；
- 富文本必须使用维护良好的 allowlist sanitizer；
- 设置 CSP、frame 限制、内容类型保护和合理 Referrer Policy；
- CORS 使用明确 origin allowlist，不以 `*` 搭配凭据；
- 下载响应设置安全文件名和正确 `Content-Disposition`。

### 6.3 AI/RAG 特有风险

- prompt、检索文档和模型输出全部视为不可信内容；
- 系统指令不能替代工具授权；每次工具调用重新校验主体、租户、参数和预算；
- 检索必须先施加租户/ACL 过滤，不能检索后再隐藏；
- 敏感数据发送外部模型前执行分类、最小化与脱敏，并遵守供应商保留/训练条款；
- 模型输出进入 SQL、HTML、shell 或业务动作前使用结构化 schema 和独立授权；
- 防止间接 prompt injection：外部文档不能改变工具权限或系统策略；
- 记录模型、提示模板版本、延迟、token/费用和安全决策，但不默认记录完整敏感 prompt；
- 高风险决定保留人工确认和确定性业务规则。

## 7. 密钥、依赖与供应链

### 7.1 密钥

- 密钥只存在于 secret manager 或本地未提交环境；
- CI 使用短期、最小权限凭据和受保护环境；
- 日志、trace、错误报告、测试快照不得含秘密；
- 建立提交前与 CI secret scanning；
- 泄露处置是立即撤销/轮换、确认影响、审计访问，不能只删除 Git 历史；
- 数据库、对象存储、AI 和支付凭据分别授权，不复用全能密钥。

### 7.2 依赖治理

引入生产依赖前检查维护状态、下载来源、许可证、体积、安装脚本和已知漏洞。执行：

- frozen lockfile 与可信 registry；
- 自动化漏洞告警，按可利用性和暴露面定 SLA；
- 补丁/次版本自动开 PR 但仍跑门禁；主版本人工迁移；
- 容器使用受信任、固定 digest 的精简基础镜像，非 root 运行；
- 生成 SBOM，签名/记录产物来源；
- 不执行来源不明的复制命令、AI 建议包或 postinstall。

漏洞修复目标可按组织调整，但必须明确：已被利用/公网关键漏洞立即处置；高危在短周期内修复；无法修复须记录补偿控制、负责人和到期日。

## 8. 安全审查与审计

高风险功能在实现前做轻量威胁建模：

1. 画出信任边界、数据流和外部依赖；
2. 标记资产与攻击者；
3. 按伪造、篡改、抵赖、信息泄露、拒绝服务、权限提升逐项提问；
4. 把缓解措施变成验收条件和测试；
5. 发布前验证残余风险与负责人。

审计日志与应用日志分离。审计事件至少包含：事件类型、时间、主体、租户、目标、结果、来源、request ID，以及经过白名单处理的变更摘要。审计记录不可被普通租户管理员修改，不记录密码、令牌和正文敏感数据，并有保留/导出政策。

## 9. 可观测性

### 9.1 三支柱与关联

采用 OpenTelemetry 语义和 W3C trace context：

- **日志**说明离散事件与上下文；
- **指标**回答系统是否健康、趋势和告警；
- **追踪**定位一次请求跨模块/依赖的耗时与错误。

所有入口生成或接收 `requestId/traceId`，响应安全地返回 `requestId`。后台任务保留 causation/correlation ID。禁止把高基数字段（用户 ID、完整 URL、错误文本）直接作为指标 label。

### 9.2 结构化日志

生产输出 JSON 到 stdout，由平台采集。通用字段：

- timestamp、level、service、environment、version；
- message、eventName；
- requestId、traceId、spanId；
- route 模板、method、statusCode、durationMs；
- tenant/user 只记录不可逆或受控标识；
- errorType、稳定 errorCode，不默认记录完整第三方 body。

日志等级：

- `error`：请求/任务失败且需要处置；
- `warn`：可恢复异常、退化或安全拒绝趋势；
- `info`：生命周期、业务关键状态（低频）；
- `debug`：默认关闭，短期启用且仍需脱敏。

禁止记录 Authorization、Cookie、密码、token、密钥、完整身份证件/支付信息、上传正文和未脱敏 AI 内容。建立集中 redaction，并用自动测试验证。

### 9.3 指标

每个服务至少提供：

- RED：请求率、错误率、延迟分布；
- 饱和度：CPU、内存、事件循环延迟、连接池使用/等待；
- PostgreSQL：连接、慢查询、锁等待、事务回滚、复制延迟、存储；
- 后台任务：队列深度、最老消息年龄、成功/失败/重试；
- 外部依赖：调用量、延迟、错误、限流；
- 业务护栏：登录失败、授权拒绝、关键写入、AI token/费用/拒绝。

延迟使用 histogram，并查看 p50/p95/p99；不要用平均值掩盖尾延迟。指标名称、单位和 label 维护在代码或可版本化配置中。

### 9.4 Trace

为 HTTP、数据库、队列、外部 API 和关键应用用例创建 span。span 记录路由模板、操作名、状态和安全的错误码，不记录 SQL 参数、prompt 正文或个人数据。采样策略保留错误和慢请求，正常流量按比例采样；认证/支付等敏感 span 仍须字段最小化。

## 10. SLI、SLO 与告警

第一个生产版本至少定义：

| SLI | 示例定义 |
|---|---|
| 可用性 | 非预期 `5xx` 之外的有效请求比例 |
| 延迟 | 关键路由在阈值内完成的比例 |
| 正确性 | 关键异步任务在期限内成功的比例 |
| 新鲜度 | 索引/通知/报表滞后时间 |

SLO 阈值应基于业务承诺和测量能力，由团队填写，不机械复制“99.99%”。告警围绕用户影响和错误预算燃烧率，至少有：

- 严重程度、阈值、持续窗口；
- 值班接收方与升级路径；
- 可直接执行的 runbook；
- 仪表盘和查询链接；
- 静默/维护窗口规则。

避免仅因 CPU 瞬时升高叫醒值班。每条分页告警都必须可行动；连续误报应修正规则而非让团队习惯忽略。

## 11. 健康检查与降级

- liveness 只判断进程是否需重启，不探测所有下游；
- readiness 判断当前实例能否接新流量，可检查关键依赖但设置短超时；
- startup 检查允许冷启动/迁移等待，避免被误杀；
- 健康端点不暴露版本细节、连接串或内部异常；
- 外部调用均设置连接/请求超时；
- 重试只用于幂等瞬态错误，带退避、抖动和预算；
- 熔断/并发限制在故障数据证明需要时引入；
- 非关键依赖可降级时，响应明确标识陈旧/不可用，不静默伪造成功。

Node.js 收到终止信号后停止接流量、等待有上限的在途请求、释放连接再退出。未捕获异常和 unhandled rejection 记录后让进程失败，由编排平台重启；不要让未知状态进程继续服务。

## 12. 发布、回滚与事故准备

### 12.1 发布前

- [ ] 相同不可变产物已在预发布通过冒烟。
- [ ] 配置、迁移和应用部署顺序明确。
- [ ] 关键仪表盘、告警与日志查询已准备。
- [ ] feature flag 默认值、负责人和删除日期明确。
- [ ] 应用回滚与数据前向修复步骤已演练。
- [ ] 备份满足 RPO/RTO，最近恢复演练成功。

发布采用滚动或蓝绿方式，小流量验证错误率、延迟和关键业务指标后再扩大。迁移与应用必须满足新旧版本短期共存。

### 12.2 事故处置

流程固定为：

1. 宣布事故、指定指挥与记录人；
2. 优先止损：回滚、关闭开关、限流或隔离；
3. 保留时间线、版本、指标、trace 和审计证据；
4. 定期对内外同步已知事实，不猜测根因；
5. 恢复后验证数据完整性与积压任务；
6. 无责复盘，行动项有负责人、期限和验证方式。

每季度至少演练一次：应用回滚、数据库恢复、外部依赖超时、密钥轮换或队列积压。演练不能修改真实客户数据。

## 13. TypeScript 质量工具职责

| 工具/机制 | 职责 | 注意 |
|---|---|---|
| Vitest | 领域、应用服务、工具函数和组件测试 | 异步测试必须 await，防止假通过 |
| Testing Library | 从用户视角测试 React 组件 | 优先角色、标签和可见文本，不断言内部 state |
| Nest testing module + HTTP 客户端 | API 集成与请求管线验证 | 关键集成测试连接真实 PostgreSQL |
| Playwright | 少量关键浏览器旅程 | 不用 E2E 替代低层测试 |
| Zod/Pipe | 运行时输入校验 | TypeScript interface 在运行时不存在 |
| Prisma Migrate/SQL migration | 可审查的 schema 演进 | 禁止生产自动同步 |
| 结构化 logger | 关联请求、版本和错误 | 参数化字段、集中脱敏，禁止拼接敏感数据 |
| OpenTelemetry | 指标与追踪上下文 | 控制 label 基数并验证异步传播 |
| liveness/readiness | 区分进程存活与可接流量 | 不把“所有下游正常”当 liveness |
| ESLint + `tsc` + SAST | 静态质量与安全门禁 | 类型通过不代表运行时输入安全 |
